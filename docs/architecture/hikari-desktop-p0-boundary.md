# Hikari Desktop — P0 边界（产品身份与第一版范围）

状态：**P0 边界草案，待人裁决；不实现。**
前置：`docs/architecture/hikari-end-state.md`（终局形态与三条红线）、`experiments/hikari-desktop/data-inventory.md`（四个问题的数据源与实测成本）、`docs/architecture/core-architecture-v0.md` §11（禁止重新引入的结构）。
本文只冻结"面板是什么、拥有什么、第一版画什么"，不重开 Memory / World / Perception 的架构问题。

---

## 0. 一句话

**Hikari Desktop 是 Hikari 的入口，不是 DSH 的控制台。独立 UI，不是独立 Runtime。**

她在那儿，是因为她有自己的连续性与记忆；不是因为她被某个聊天窗口托管。

---

## 1. 产品身份

### 1.1 方向

- **B 为主（Companion）**：首页以"她现在怎么样"为中心——在线、在做什么、最近记住/观察/改变了什么、有没有事等你。
- **A 为辅（Control Center）**：记忆、认识、拒绝、存储健康这类管理视图放二级页，不占首页。

判据只有一条：**打开后第一屏回答的是"她现在怎么样"，而不是"系统健不健康"。** Token 用量、插件状态、日志级别属于后者，不进第一屏。

### 1.2 与 DSH 的关系

```
Hikari Desktop   独立前端 · 人的入口
      │  只读取数（第一版：读磁盘）
Hikari Core      memory / world / perception / project-watch / activation
      │  Service · Event · 工具
DSH Adapter      模型接入、工具执行、插件宿主、会话日志
```

- DSH 是**能力宿主之一**，不是 Hikari 的存在前提。换掉 DSH，Memory 文件与面板都还在；只有会话日志那部分（findings、对话）会失效。
- 面板**不拥有** Memory、不拥有 findings、不拥有对话；它渲染它们。
- 反向约束同样成立：**Hikari Core 不依赖面板**。删掉面板，记忆本体一点不损失。

### 1.3 三条硬约束（继承 `hikari-end-state.md` §5.2）

1. **只读**：P1 不能改、不能删、不能注入。能改的地方不是"看它"，是"操作它"。
2. **渲染，不是真源**：所有数字现算；允许缓存，但缓存必须可丢弃、可由文件大小与偏移校验，不能成为第二份真源。
3. **不做第二套持久化**：不建数据库、不写"快照文件当数据源"、不新增后台进程。

## 2. 数据所有权

| 数据 | 归谁 | 载体 | 面板能不能读 |
|---|---|---|---|
| 记忆（记录、修订链） | Memory Store | `memory.jsonl` | 能（P1，直接读） |
| 被拒写入 | Memory Store | `memory.rejections.jsonl` | 能（P1，直接读） |
| 认识（findings 四态与变化） | World | DSH 会话日志的 `plugin:hikari/finding` | 能但贵（需读口，见 §4） |
| 观察·窗口切换 | Perception | 无结构化载体（只有改写成提示的文本进会话日志） | 不能（只能显示文本） |
| 观察·仓库变化 | project-watch | `trace.jsonl`（产线 `tracePath` 已打开，实测 567 行 / 36,978 B，字段 `at/kind/head/dirty/changed/headFrom/headTo`） | 能（P1，但文件现在住在 `experiments/…/tmp/`，位置待定） |
| 未完成的事 | **未定义** | 无 | 不能 |
| 对话 | DSH agent-loop | 会话日志 | P1 不读；P2 走会话通道 |

**写一律走既有工具。** 面板若要"纠正一条记忆"，只能将来通过 `revise_memory` 产生一条新记录——不许绕过工具层直接写 `memory.jsonl`。这条不是 P1 的功能，是所有权声明。

## 3. 五个区域（+ Conversation）

每格标：回答什么 / P1 数据来源 / 今天缺什么。

| 区域 | 回答什么 | P1 数据来源 | 现状 |
|---|---|---|---|
| **Home** | 她在不在、上次活动多久前、记忆几条、几条发生时间未知、最近几次拒绝、有没有事等你 | `memory.jsonl` + `memory.rejections.jsonl`；"在线"用"文件最后写入时间"近似 | 记忆/拒绝能（**生产库今天 0 条**，见下方注）；"等你的事"**今天无来源** |
| **Memory** | 她记得什么、什么时候记的、被谁修订过、为什么被拒 | `memory.jsonl`（`seq`/`recordedAt`/`supersedes`/`occurredAt`）+ `memory.rejections.jsonl` | **能**，已有 `viewer/render.mjs` 的 `buildView` |
| **World** | 她认为什么成立、依据是什么、哪些被推翻、怎么变的 | 会话日志的 `plugin:hikari/finding`（按**（会话, findingId）**分组、按 `seq` 排序；`findingId` 只在会话内唯一） | 能但贵：本工作区 99 会话 / 90.8 MB / 52,311 帧 / 63 条 finding |
| **Awareness** | 她最近被什么触发过、忽略过什么 | 仓库变化：`experiments/hikari-project-watch/tmp/trace.jsonl`（567 行，`at/kind/head/dirty/changed/…`）；窗口切换：会话日志里 `[Hikari 自主观察 HH:MM:SS]` 的提示文本 | **半能**：仓库侧有结构化轨迹可读；窗口侧只有文本 |
| **Activities** | 她做过什么、结果如何、哪些没做完 | 无 Hikari 自己的来源：会话日志里有 `tool/call` / `tool/result`（宿主的执行记录）与 `todo/write`（宿主的待办，333 条，无 owner/due）——它们都不是"Hikari 的行动"，怎么算要先裁决 | **第一版不画**；若 P2 要画，先定"什么算她做的" |
| **Conversation** | 跟她说话、纠正认识、确认行动 | 不在 P1 | 依赖"在场（时间）/在等（未决）/该不该打扰（判断归属）"，见 §5 P2 |

注：生产库 `C:\Users\29719\.dsh\hikari\memory` 今天只有 `memory.meta.json`（`recordCount: 0`），没有 `memory.jsonl`；2 条记录 / 4,144 B 是实验库 `experiments/m2c-live/store/memory.jsonl`。所以 P1 的"≥2 条真实记忆"在真实库上**今天没有数据可验**——要么先在真实运行里写两条，要么 P1 的验收对象明确写成实验库。

**第一版两条硬规矩：**

1. 没有来源的区域，显示"我现在还不知道"，不画空列表——空列表会被读成"没有欠着的事"，那是假信息。
2. `occurredAt` 为 `null` 一律渲染成"发生时间未知"，绝不渲染 1970（`viewer` 已这么做，面板沿用）。

## 4. 读口：面板怎么拿到 DSH 里的东西

记忆那一格没有争议（读文件）。真问题在 World 与 Awareness：数据在 DSH 会话日志里。

| 方案 | 怎么取 | 代价 / 耦合 | 判 |
|---|---|---|---|
| **A. 只读磁盘派生** | 记忆读 `memory.jsonl`／拒绝读 `memory.rejections.jsonl`／仓库观察读 `trace.jsonl`／认识变化解 `session.v4.jsonl.zstd` 按 `type` 过滤 | 耦合 DSH 日志格式（`session.v4`）；每次全量解码不可接受（复测 52,311 帧 / 90.8 MB），需按文件大小+偏移做增量；宿主升级格式就断 | **P1 采用** |
| **B. 进程内只读服务** | 插件里开一个只读 HTTP/SSE，面板订阅 | 干净、可实时；但这是**新面**，要按 governance 走 L3 检查，且与"不起服务、不做常驻"冲突 | P1 不做；等"实时/在线"成为真实需求再评估 |
| **C. 宿主 HTTP API** | 若 DSH 已有读会话/投影的接口，直接消费 | 不新增面；但语义是"DSH 会话"而非"Hikari 认识"，且该接口是否可用未证实 | 先探一次，可用则优先于 A |

推荐：**P1 = A（带增量与缓存），C 若被证实可用则替换 A 的取数实现，B 留给 P2 的 Presence。**

一条边界：无论走哪个方案，面板**只读**；"订阅事件"也必须以"读派生出的记录"实现，不许把面板变成事件消费者（那会让她的话变成"面板说"）。

## 5. 分期与判据

| 阶段 | 内容 | 判据（可清点） |
|---|---|---|
| **P1 独立只读面板** | 单页（或一组静态文件）：Home + Memory + World；Awareness 只显示"最近被唤醒过几次"；Activities 显示"还不知道" | ① 打开一个本地页面，能看到 ≥2 条真实记忆及其修订链；② 能看到拒绝记录（含错误码与摘要）；③ 能看到 findings 的当前四态与至少一条状态变化；④ "未完成"显示"还不知道"；⑤ 不新增进程、不新增服务、不新增依赖、不写任何文件 |
| **P2 Presence + Conversation** | "她在场/她在等/她该不该打扰你" + 对话区 | 门禁：时间、未决事项、判断归属这三件各至少一片落地；否则不做 |
| **P3 Desktop Shell** | 常驻窗口、通知、快捷入口 | 门禁：P2 已有真实日常使用 |

**P1 的第一份验收对象就是用户看的那四件事**：最近记住什么（能）、观察到了什么（半能，如实标注）、哪些认识变了（能）、还有什么没完成（**2026-11-06 起能**，见下）。

### 5.1 P1 追加（2026-11-06）：Goal 与两种"最后时间"

Goal（`7586602`）落地后，面板原本"还不知道"的第四件事有了真数据源；用户复核提交时又指出面板缺两项。三处改动都只动 `hikari-native/panel/build.mjs` 与它的测试：

| 改动 | 判据 |
|---|---|
| 读 `<记忆库的兄弟目录>/goal/goals.jsonl`，按同编号最后一行折叠，分出 `open` / 已收口；Home 增加"还没做完的事（N 条 / 共 M 条承诺）"，新增"她答应过什么"一节 | 能看到她真实写下的承诺原文、备注与立下时间；目标库不存在时明说"还没立过任何承诺"，不显示空壳 |
| 把"最后一次痕迹"拆成**最后一次被叫醒**（会话日志最新记录，说明她还在运行）与**最后一次留下东西**（记忆 / 拒绝 / 目标 / 有变化的仓库轨迹） | 她只醒过、什么都没写时，前者是新的、后者仍是旧的——这一格不再用一个数代表两件事 |
| 仓库轨迹只取"有变化"的行计入"留下东西"的时间 | project-watch 每 30 秒写一行 `quiet`，若用文件 mtime，这一格永远是"刚刚"——那是采样，不是她的动作 |

原来的判据 ④（"未完成"显示"还不知道"）因此作废，改为：**能看到她写下的 open 目标原文，并在没有 Action 时明说"承诺不是行动"**。§6 的"不为了把五个区域填满而画空壳"仍然有效——这一格有真数据才填，没有就留白。

## 6. 明确不做（P1）

- 不做控制台：不改、不删、不注入、不直接写 `memory.jsonl`。
- 不做实时：不常驻、不订阅事件、不开服务。
- 不做通知。
- 不做账号、不做云端、不做多用户。
- 不做第二套真源：不建数据库、不写"数据源快照"、不在面板侧保存状态。
- 不为了把五个区域填满而画空壳。
- 不改任何 Hikari 插件与 DSH Runtime 的契约（P1 若需要改 `viewer/render.mjs` 之外的生产代码，另立一片）。
- 不做 Conversation 的替代聊天窗。

## 7. 与冻结原则的对照

| 冻结原则 / 禁止项 | 本方案 | 说明 |
|---|---|---|
| 不自动注入（end-state 红线 2） | 不触碰 | 面板不向任何会话注入内容 |
| 不自动沉淀（红线 3） | 不触碰 | 面板不写记忆 |
| 不造中央大脑 / 中央判断域（§11） | 不触碰 | 面板只渲染，不判断"哪条重要" |
| 单一全局 Memory Store | 保持 | 面板读那个文件，不另建库 |
| "Provider 不决定 Consumer" | 保持 | 面板是 Consumer，World/Memory 仍是 Producer，各自不持有路由图 |

## 8. 待人裁决（P1 开工前）

1. **取数范围**：P1 是否允许读 DSH 会话日志（接受格式耦合）？若不允许，World / Awareness 两格就只能是"还不知道"，P1 缩成 Memory 一格。
2. **"在线"怎么表示**：用内存文件最后写入时间近似（并标注"这是近似"），还是这一格先留白？
3. **形态**：单文件 HTML（双击打开，受 `file://` 限制）／本地起一次性的只读静态服务（严格说违反"不起服务"，但可用后即关）／DSH 客户端页。三者取舍决定 P1 的实现量级。
4. **"面板里纠正记忆"**是否进入路线图——若进，排 P2，且必须走 `revise_memory`，不新开写通道。

这四条定下来 P1 就能开工，所以结案时不再单列"是否动工"与"读口走哪条"：读口由第 3 条（形态）决定——单文件 HTML 只能读磁盘（§4 方案 A），一次性静态服务可以在同一个进程里读（A 或 B），"在线"一格则取决于第 2 条。

### 8.1 已裁决（2026-11-05）

| 条 | 裁决 | 说明 |
|---|---|---|
| 1 取数范围 | **都读**：Hikari 自己的文件 + DSH 会话日志 | 会话日志只用来算"认识变化"与"被唤醒次数"；格式耦合写进页面页脚，不隐藏。日志目录读不到时那两格显示"没找到"，不是"她没有"。 |
| 2 "在线" | **文件最后写入时间近似**，并标"近似" | 没有任何进程自报在场；面板不假装知道"她现在醒着吗"。 |
| 3 形态 | **单文件 HTML** | 只有它同时满足 §5 判据⑤（不加进程、不加服务、不加依赖、不写文件）。双击打开即可，关掉页面就等于关掉面板。 |
| 4 面板里纠正记忆 | **不进 P1** | 写入口仍然只有 `write_memory` / `revise_memory` 两个工具；面板侧一个字节都不写。 |
