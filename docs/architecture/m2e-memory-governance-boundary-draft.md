## 1. 为什么看它

M2-b 管「怎么写入」，M2-c 管「怎么找回与修订」，M2-d 管「检索粒度」。三者共同的前提是
**写入只记成功的**：一次被校验拒绝的写入，除了抛给模型的一条错误消息，什么都不留。
灵枢在这一点上比我们走得远——它把「决定不记」本身也当成一条可审计的事实。这是本文
唯一真正想借的东西。

## 2. 灵枢的治理机制（代码事实）

| 机制 | 它怎么做 | 证据 |
|---|---|---|
| 主动遗忘闸门 | `mdcg_remember(gated=true)` 先过「三问 → 四态」：ACCEPT 落盘 / MERGE 并入既有（去重强化，不新增节点）/ DROP 丢弃低熵噪音 / DEFER 待定；**四种结果都写 `_forgetting.jsonl`**，可审计 | `src/lib/mdcg_client.ts:288-301` |
| 审核队列 | `mdcg_propose` / `mdcg_review_list` / `mdcg_review_records` 入列、查询、看审计；裁决 `review_decide` 属管理类，需 `can_admin` | `lib/tools.js:36-38` |
| 保护与遗忘史 | `mdcg_protect` 给节点上保护；`mdcg_forgetting_history` 查遗忘记录 | `lib/tools.js:39` |
| 负记忆与未决 | `mdcg_rejected`（被否决的内容）、`mdcg_unresolved`（悬置问题）各自成面 | `lib/tools.js:34-35` |
| 裁决只追加 | `verify(nodeId, evidence, verdict)` 只写 `rejected`/`contextual`，**不得改被验证的内容** | `src/lib/mdcg_client.ts:309-313` |
| 写入单元收窄 | 写路径声明 `as_unit`（如 `record`、`verify`），声明不得写 `self`/`anchor` 层 | `src/lib/mdcg_client.ts:298-301`、`:310-313` |
| 自动沉淀 | `ctx.on('session/event', …)` 把会话事件经 `mdcg_remember(gated=true)` 写进 `contextual` 层 | `lib/hooks.js:918` 一带 |
| 自动注入 | `autoRecall` 走 `system-prompt/assemble` 瀑布，**每次请求自动注入最近记忆时间线**，默认开启 | `lib/hooks.js:43-46`、`lib/index.js:68` |

## 3. 逐条映射：借 / 不借 / 只借一半

判定标准只有一条：**能不能落在 Hikari 已冻结的十项前提与架构底线上**，而不是「它做得好不好」。

| 灵枢机制 | Hikari 现状 | 判断 | 理由 |
|---|---|---|---|
| 被拒写入也留痕（DROP/DEFER 入账） | 校验失败只 `throw new Error('MEMORY_*: …')`，不留任何记录 | **借** | 它与「模型判断是否值得保存」不冲突：判断仍由模型做，工程只是把「这次没存成、以及为什么」记下来。可让模型下次不重复同类尝试，也让人能事后看出记忆为什么缺。 |
| 裁决只追加、不改被裁决内容 | `revise_memory` 已经是「新行 + `supersedes`」，旧行一字不动 | **已有，可扩展** | 语义一致。若将来要表达「这条记忆被判定为错」，应写成一条新记录（裁决记录），而不是给旧行加字段。 |
| 四态分诊（ACCEPT/MERGE/DROP/DEFER） | 无 | **不借** | 分诊是「要不要记」的判断，我们的前提是这件事归模型。工程侧只做校验，不做取舍。 |
| 审核队列（propose/review/decide） | 无 | **不借（本阶段）** | 它需要一条「人/管理员裁决」通道。Hikari 目前没有面向人的输入面，`core-architecture-v0.md` §11 也明确不许重新引入 Generic Human Input。要做得先有归属方，那是另一个架构问题。 |
| protect / forgetting_history | 无 | **不借** | 二者都预设「记录可以被删或降权」。Hikari 是 append-only，能表达的只有墓碑（新行标注「此条已作废」），不是删除；而「作废」在我们这里已经是 `supersedes` 的语义。 |
| rejected / unresolved 两个面 | 无 | **不借** | 它们是围绕「审核流」与「未决问题」建的；我们没有审核流，未决问题属于判断层（ClearAI），不属于 Memory。 |
| 写入单元收窄（as_unit） | 工具层不暴露工程字段，`store.append` 有白名单 | **已有等价物** | 我们的等价物是 schema + 白名单双门（M2-b §2.2、`store.mjs:475-480`），不需要再引入「单元」概念。 |
| 自动沉淀 | 不提取对话（前提 8） | **不借** | 直接冲突。 |
| 自动注入 | 不自动注入（前提 7） | **不借** | 直接冲突：注入会造出一条没有归属、没有 scope 的证据通道。 |

## 4. M2-e 的建议范围（草案，未冻结）

只做两件事，其余明确不做：

1. **被拒写入留痕**：把「校验拒绝」变成一条可查的事实，至少包含：时间、被拒的错误码、
   模型给的正文摘要（截断）、被拒的字段名。这让「记忆为什么缺」可回答。
2. **撤回/作废的表达**（若需要）：只允许追加一条新记录表达「此条不再作为依据」，不改旧行。

明确不做：删除、自动过期、自动分类、审核队列、注入、跨系统对接、向量检索。

## 5. 三个必须先定的问题（交给人）

这三条决定了 M2-e 是「小改动」还是「改记录形状」，不能由执行者自己选：

1. **被拒留痕放哪里**：放进同一个 `memory.jsonl`（需要给记录加 `type` 或让 `text` 承载非记忆内容），
   还是另开一个文件（就出现第二个持久面，与「单一全局 Memory Store」的前提张力）。
2. **「被拒」算不算一条记忆**：算，则它可以被检索、被引用，模型可能把「被拒的记录」当依据；
   不算，则它只是一份诊断日志，不参与检索。
3. **要不要「撤回」**：`supersedes` 表达的是「有新版本替代」，不是「这条是错的」。
   若两者都要，就得在记录里区分「被替代」与「被判定为错」。

## 6. 与冻结原则的对照

| 冻结前提 | 影响 |
|---|---|
| 1 Memory 由 Hikari 全局拥有 | 不受影响：留痕仍在本插件的存储里 |
| 2 单一全局 Memory Store | **有张力**：另开文件就是第二个持久面（见 §5.1） |
| 5 工程负责校验/ID/时间/持久化/完整性 | 不受影响，反而强化：拒绝也能被审计 |
| 6 append-only | 不受影响（留痕也是追加） |
| 7 不自动注入 | 不受影响（灵枢的注入机制不借） |
| 8 不自动提取 | 不受影响（灵枢的沉淀机制不借） |
| 9 不自动判断过期 | 不受影响 |
| 10 不改变 World 的 Findings 所有权 | 不受影响 |
