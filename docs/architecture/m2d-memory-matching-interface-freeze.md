# M2-d 记忆检索匹配口径：实施边界冻结

**日期** 2026-11-05
**前置** `experiments/m2d-matching/matching-probe.md`（探针读数与结论「部分够」）、`docs/architecture/m2c-memory-discovery-interface-freeze.md`（M2-c 冻结面，本次修订它 §2.1 与 §6）
**状态** 已评审并实施（2026-11-05）；验证记录 `docs/development/m2d-verification.md`。本文只冻结「匹配与排序」这一片，不重开 M2-c 的工具形状、参数集合、错误码。§3 的四处修订已落到 M2-c 冻结面正文（实际行号见下表「落地位置」），不是只写在修订表里。

## 0. 一句话范围

把 `search_memories` 的命中判定从「整串子串」换成「拉丁词元按词元包含 + 中文片段覆盖率 ≥ 0.25」，排序从「只按 `seq` 倒序」换成「先按匹配强度、再按 `seq` 倒序」；`get_memory`、写入工具、store、错误码一律不动。

**本片级别 B（普通 capability 的边界修订）**，owner 是 `hikari-native/memory/recall.js`。

## 1. 为什么改、为什么不改别的

探针（`experiments/m2d-matching/matching-probe.md`）在 M2-c 的现场记录上给了三组读数：

- 现状 A（整串子串）在 B1 的四条真实 query 上 0 命中——这是 M2-c 现场复现，不是构造；
- 纯 bigram（F）能救回中文问法，但在 7 条期望不命中的 query 上误命中 3 条（`TypeScript 编译错误`、`npm test 跑多久`、纯英文问法），成因是拉丁字母的 bg 对在代码词里遍地都是（`supersedes`、`store`、`delete`、`script`）；
- 单字覆盖率（D）12/12 全中却误命中 4 条，`完全不存在的词` 靠 `完/不/存/在/的` 过线——性质上不可用，不是阈值问题。

所以本片只取 F 的中文侧能力，拉丁侧换成「词元包含」这一约束。**不做**：分词（需要词表）、同义词/语义（需要词表或向量）、跨语言翻译（需要翻译层）、词干还原。这些留给 M2-e，见 §7。

**为什么是「词元包含」而不是「词元相等」**：正文里 `revise_memory` 是一个词元，模型写 `revise` 应当算命中；`typescript` 与 `script` 却必须不算——包含关系同时满足这两件事，相等关系做不到第一件。

**为什么阈值是 0.25 而不是 0.30**：`memory 修订 规则 是什么` 的中文侧四个片段里只中 `修订`，0.25 恰好放行、0.30 挡掉；而 0.25 在 19 条 query 上没有引入任何误命中（`matching-probe.md` 汇总表）。这是本集合决定的线，不是理论最优。

## 2. 冻结面

### 2.1 匹配强度（新增纯函数）

```js
// 返回 0..1 的强度分；不命中返回 null。
export function matchStrength(query, text) → number | null
```

规则，按顺序：

1. `q = String(query).toLowerCase()`；`t = String(text).toLowerCase()`。若 `t.includes(q)` → 返回 `1`（**整串子串是快速路径，也是最强的命中**）。
2. 把 `q` 按标点/符号/空白切词（`/[\s\p{P}\p{S}]+/u`）。其中匹配 `/^[a-z0-9_.#/-]+$/u` 的片段是**拉丁词元**；其余片段（中文等）合成「中文侧」。
3. **拉丁词元全部要被 `t` 的某个词元包含**（`t` 用同一套分隔符切词）：任一词元不满足 → 返回 `null`（不命中）。
4. 中文侧切成「片段集」：每个非拉丁片段内取相邻字符对（bigram）；长度为 1 的片段取该字本身。
5. 中文侧片段集为空 → 返回 `null`（只有拉丁词元且未走快速路径时，按「拉丁词元全中」算 `0.5`，见 2.2 说明）。
6. 覆盖率 = 命中片段数 / 片段集大小；**< 0.25 → 返回 `null`**，否则返回该覆盖率（0.25 ≤ 强度 < 1）。

### 2.2 强度分与排序

- 强度分就是 2.1 的返回值。快速路径固定 `1`，片段路径落在 `[0.25, 1)`。
- **只有拉丁词元、没有中文侧的 query**（例如 `revise`、`memory`）：快速路径未中但词元全中时强度记 `0.5`。这是刻意的一档低分——证据只有一个词，不该压过「整串命中」。
- 排序：**强度倒序；强度相同时 `seq` 倒序**。`seq` 倒序仍是同强度内的唯一秩序（`occurredAt` 大量为 null，不能用来排）。

### 2.3 不改的东西（逐条钉住）

- 过滤顺序不变：匹配 → 时间窗 → `headOnly` → 排序。时间窗对 `occurredAt === null` 仍一律不命中。
- `results` 每条的五个键不变：`{memoryId, snippet, occurredAt, validHint, supersededBy}`；`snippet` 仍是 `text` 前 120 个 UTF-16 码元、截断补 `…`。
- 分页语义不变：`limit` 夹到 1–20；`nextOffset` 只在还有更多时出现。
- `get_memory`、`write_memory`、`revise_memory`、`search_memory`、`read_memory` 一字不动。
- `hikari-native/memory/store.mjs` 不动；不新增字段、不引入新的持久化。
- 错误码表不变（`MEMORY_QUERY_EMPTY` / `MEMORY_INVALID_TIME` / `MEMORY_INVALID_RANGE` / `MEMORY_UNKNOWN_ID` / `MEMORY_NOT_A_MEMORY`）。

## 5. 验收（实施时必须全绿）

1. 现有 `hikari-native/test/memory-recall.test.mjs` 12 用例全部仍通过（尤其 `[2]` 的 `ableGi` 子串断言、`[3]` 的时间窗、`[4]` 的 `headOnly`）。
2. **B1 四条现场 query**（`hikari 记忆修订`、`revise memory 旧记录`、`记忆 修订 约定`、`记忆修订 只能修订哪一条 旧记录是否改动`）在 1 条记录的 store 上各命中 1 条。
3. **无关 query 不命中**：`完全不存在的词`、`部署脚本 代理`、`TypeScript 编译错误`、`今天的天气`、`npm test 跑多久`、`会议纪要 待办事项`、`how to revise a memory without losing history` 在 2 条记录上均返回空集。
4. **强度排序**：一条「整串命中」与一条「片段命中」同时存在时，整串的排在前面；同强度按 `seq` 倒序。
5. **`snippet` 不变**：仍取前 120 个 UTF-16 码元，截断补 `…`（emoji 计 2）。
6. **只有拉丁词元**的 query 若整串不是正文子串（如写成 `revise-memory`）走 0.5 档：两个词元都在正文词元里，仍命中，但不排在整串命中前面。注意 `revise` 这类词元本身就是子串（正文里有 `revise_memory`），走的是快速路径、强度为 1。
7. 全量 `npm test` 不少于实施前的 1131 tests / 1127 pass / 0 fail / 4 skip（M2-c 结束时的基线）。

> 实施时校正：第 6 项原例写的是 `revise`，但 `revise` 是正文 `revise_memory` 的子串、走快速路径得 1，够不到 0.5 档；已改成 `revise-memory`，`revise` 如实记为 1。见 `docs/development/m2d-verification.md`。

## 6. 明确不做

- 不做分词、词干、同义词、语义/向量检索、跨语言翻译。
- 不改返回形状、不加 `score` 字段（强度只用于排序，不出现在结果里）。
- 不改 `search_memory`（World findings 侧）的匹配：那边是 finding 的字面检索，与记忆无关。
- 不加索引、不缓存、不改 store。

## 7. 留给 M2-e 的缺口（本片不解决，写清楚）

1. **纯换义**：`两次修改同一条记忆` 的 8 个片段里只命中「同一」一个（1/8 = 0.125，低于 0.25），字面口径必然 0 命中；正文写的是「修订」「链头」「旧记录」。
2. **跨语言**：正文中文、问法纯英文时 0 命中（拉丁词元 `how`/`without`/`history` 不在正文词元里）。
3. **极短 query**：`记忆` 这类单字/双字词退回整串子串，正文没有该串就不命中。

这三条都是性质问题，不是阈值问题——提高覆盖率下限能减少误命中，但一条也救不回来。

**三条出路的代价（各自独立，不能叠加成"更好的字面"）：**

| 出路 | 新增依赖与体积 | 新失败模式 | 对现有口径的影响 |
| --- | --- | --- | --- |
| 中文分词 + 同义词表 | 分词器与词典（典型 5–20 MB，随插件分发）；同义表要人工维护，否则只覆盖常见几组 | 分词边界错一处就召回抖动（`修订只能改链头` 切错会把关键词切碎）；同义表扩得过宽会把无关记忆拉进来，等于用误命中换召回 | 覆盖率单位从 bigram 变成词，**0.25 不再可比**，必须重新标定并重跑 19 条 query 的矩阵；排序仍可用「整串最高、词级次之」两档 |
| 多语嵌入（本地或远端向量） | 本地小模型约 100–400 MB，或每次检索一次远端调用；存储要加向量列与新索引文件（append-only 仍可行，但 `store.mjs` 的十字段要扩） | 模型版本漂移 → 同一 query 结果变化（不可复现）；批量重建索引的启动开销；记忆正文离开进程（隐私面变大） | 阈值从覆盖率变成余弦相似度，**与字面强度不可直接比较**，需要一个融合规则（例如字面命中优先、向量只补召回） |
| LLM 语义重排 | 每次检索一次模型调用（延迟秒级、有费用） | 同一 query 两次结果可能不同（不可复现）；同步工具返回要等模型，超时就得降级；只能对**候选**重排，救不回首轮 0 召回 | 不改匹配与排序定义，但检索从"纯本地、确定性"变成"依赖外部服务"，`§5` 验收里的可重复性一条要重写 |

任一方案都会改动 §2 的强度定义或 §5 的验收，等于重开冻结面——所以放在 M2-e，而不是在本片里加一个"可选开关"。

## 9. 待人决定

1. **阈值 0.25 是否接受**：它在 19 条 query 上 0 误命中，但样本只有 1–2 条记录。若不接受，可先只冻结排序维度（强度 = 整串/片段两档）而不冻结具体数值——但那样 B1 的 `memory 修订 规则 是什么` 会落到 0.30 以下不命中。
2. **要不要把「返回 `score`」也纳入本片**：现在强度只用于排序、不出现在结果里。如果以后要让模型自己判断「这条有多接近」，就得加键——那是返回形状变更，本片明确不做。
