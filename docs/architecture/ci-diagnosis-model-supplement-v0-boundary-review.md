## §0 结论

- 本文件只定义**产品任务与边界**：模型在什么位置介入、能输出什么、不能输出什么、出问题时怎么办。**不定义接口、不写实现、不接产品路径。**
- 模型的唯一位置：诊断 owner 已经判出 `insufficient-evidence` 时，**补一条「值得复查什么 + 依据 + 还缺什么」**。规则判出的另外三支（`check-commit-alignment` / `inspect-run-steps` / `inspect-own-action`）**不经过模型**。
- **§7 五项未决已全部裁决**（2026-10-17）：消息形状、单一分支、可观测性（§10.1/§10.2/§10.4）；材料按 **3 个请求采全**（commit 清单+patch / jobs / 失败步骤日志，§10.8）；连续失败 **v0 不退避**（只加可观测性与复访触发条件，§10.9）。
- **同日一处边界被推翻（§10.8）**：第三条材料不是「多花配额」——`/actions/jobs/{id}/logs` 匿名返回 **403 `Must have admin rights to Repository.`**（公开大仓库同样如此），因此 **Human 裁决引入 admin 级 GitHub 凭据**，越过 `src/github-ci/github.ts:28-30` 那条「凭据是这一片不做决定的事」。凭据契约、最小权限、失败语义与安全清单写在 §10.8，**最小权限集合尚未用真 token 实测**。
- **实现评审的硬边界已定（§11）**：材料采集**继续归 `github-ci`**（唯一持有凭据、额度与 HTTP 的 owner），不新建采集 owner；补充模块不持有 token、不发请求；**材料失败不得让已经成立的 CI 失败事实变成不可用**（观察与材料是两次独立获取）；认证失败按「未配置 / 无效或权限不足 / 网络或服务端错误 / 日志失败」四类分别处理，且**必须读响应头与体、不能只看状态码**。**本轮仍然只有文档，没有产品代码。**
- **真 token 已验（§12.11，2026-10-18）**：认证后 `core` **5000/h**（匿名 60/h）；`/commits/{sha}` 一个请求就带 `files[].patch`；日志是 **302 → Azure Blob 签名地址 + `text/plain`**，签名地址**不带凭据也能取**，完整日志 140 KB 且**含 ANSI**，而**尾部是收尾噪音、不是失败断言**——据此把「保留尾部」改成「按失败步骤边界切」。
- **材料契约的候选形状已写出（§12，2026-10-18）**：输入绑在已观测的那条 run 上（三个字段全过形状检查，URL 只由它们拼）；每份材料各自带 `present` / `missing(reason)` / `pending`，**提供侧不判断够不够**；三个请求、材料总时限 20 s、日志流式截断到 64 KiB、不重试；**材料失败是值不是异常，且不改变观察**。
- **三项裁决已冻结（§12.8，2026-10-18 Human 裁决）**：**Q1** 采用「补充模块取材料、确定性诊断不动」，并连带冻结两条失败隔离约束（补充模块把一切失败转成「不附加」；**attention 在投递前对整段可选补充再设一道局部失败边界**，未预期异常只记录、不阻断原通知）；**Q2** 资格规则 =「`jobs` + `changedFiles` 均在场且可用才允许尝试，`log` 缺失本身不否决」，且「在场」= 成功取得并通过结构校验（空 `changedFiles` 是真实空结果，不是失败）；**Q3** `pending` 本次不附加、不等待第二轮。术语纠正：`insufficient-evidence('commit-comparison-indeterminate')` 是**诊断的判断结果，不是世界事实**。
- 模型输出是**候选**，不是决定：结构不合、引用对不上材料、超时、模型不可用，一律 **fail-closed** 回退到原行为（只发普通通知）。
- 本文件**不采用** `likelyCause` 分类准确率作为验收指标——那是 §2.10 实验的代理指标，与产品要解决的问题不是同一个。
- **设计与契约已冻结**（§10，2026-10-17 Human 裁决）：同一条通知 + 可选补充段且自带身份声明；只开放 `commit-comparison-indeterminate` 一支；预算与开关都是**显式参数、无插件默认值**（首轮推荐 180 000 ms）；取消语义两分（客户端取消 ≠ 服务端推理终止）；验收分「不添乱」与「有价值」两段，后者用真实红 run 且**调过提示词就必须换材料复测**。
- **消费侧已实现（§13，2026-10-18）**：补充模块与插件落进 `repository-ci-diagnosis-proposal`，attention 在投递前追加并在外面加一道局部失败边界；产品级失败注入证明「补充成功 / 补充失败 / 不调用模型」三种情形都**恰好投递一条**。**但没有接线**：resident 不传模型端点、不传 token、不传预算参数，所以生产行为与本片之前逐字相同。§10.5 的 **B 段（有价值）尚未开始**。

## §1 为什么先写这个文档

三轮验证（§2.8 / §2.9 / §2.10）加一次外部独立评审，指向同一句：**「模型能做这件事」与「模型该在生产链路里做这件事」之间，缺的不是模型能力，是任务定义。**

- 第一轮（§2.8）：不给规则，按登记字段 58%——能判，但程序不稳；守在认知上的边（不编造、不认诱饵）没破。
- 第二轮（§2.9）：把规则逐字给它，语义 12/12——**复述不是瓶颈**，瓶颈转到输出格式。
- 第三轮（§2.10）：规则抽走、材料长大，判别空间 13/15 = 86.7%——有推论信号；**但实验要求它做的是「失败归因分类」，产品要的是「值得复查什么」**。
- 外部独立评审（2026-10-17）：门槛达成、能力信号成立、**产品验收不成立**；最强的反对意见不是样本量，而是**任务错位**。

任务错位的一个直接证据：实验里的字段叫 `likelyCause`（「可能原因」），这个名字是实验作者起的——产品并不问原因。

因此本文件把产品要的那件事先写死，再谈实现与实验。

## §2 任务定义

**触发面**（只有这一条路进得来）：

1. 一次 CI 失败已被 relevance 判为 `relevant`（工作焦点逐字命中，或人给的配对命中）；
2. 该 run 尚未投递过（去重语义不变）；
3. 诊断 owner 的规则判定为 `insufficient-evidence`，且 `missing` ∈ {`no-github-ci-facet`, `relevance-not-established`, `commit-comparison-indeterminate`}。

**模型要回答的唯一问题**：

> 就现有材料，**这次失败值得人先复查哪里**；依据是哪几行材料；还缺什么证据才能更进一步。

**它不回答**：失败原因是什么、谁引入的、该怎么修、要不要回滚、值不值得重视。

**输出必须包含四段内容**（这是内容要求，不是接口字段）：

1. **复查目标**：一个具体位置（文件 / 步骤 / 记录），不是「看看日志」；
2. **依据**：材料原文引用，逐字可查；
3. **为什么值得看**：只能用「与…一致 / 更像 / 指向」这类可能语气；
4. **还缺什么**：材料里没有、但能决定结论的那几项。

## §3 权限边界

允许：

- 在 `insufficient-evidence` 之上**追加**一条候选建议；
- 说「我判断不出」，即保持 `insufficient-evidence`；
- 引用材料原文。

禁止：

- 改变规则已判定的分支（不得把 `check-commit-alignment` 改成别的，也不得在三支规则结论之外插话）；
- 声称材料之外的事实（提交 id、文件名、日志行、时间）；
- 因果断言；
- 行动建议（「应该先做 X」）；
- 触发任何执行能力（模型输出不进入执行器，不构成 mandate）；
- 扩大自己的调用面（不新增工具、不发起材料之外的请求）。

## §4 fail-closed 契约

任一条件不满足 → 丢弃模型输出、回退到今天的确定性行为（普通通知），且**不改变投递计数与去重语义**：

- 结构可解析；
- 每条引用能在材料原文里找到（空白归一后逐字匹配）；
- 四段齐全，且没有出现被禁内容（因果 / 行动 / 材料外事实）；
- 在时限内返回；模型不可用、超时、限流都算未满足。

**「模型没参与」不留新的事实 kind，也不写 chronicle**——避免把模型行为写成领域事实。

## §5 材料契约（模型能看见什么）

由代码准备好、模型不推断：

- 失败 run 的字段、jobs 与失败步骤；
- 失败步骤的日志片段（截至失败点）；
- 本次改动的**文件清单 + 命中文件的 patch**（截断规则与采集成本见 §10.8）；
- 同一 `head_sha` 的尝试、更早提交上的失败记录；
- **对应关系**（结构性、由代码算）：失败测试文件、改动文件、共享路径段。

原则：**能用代码算出来的关系，不交给模型推断。**

这条原则有直接证据：§2.11 记录的那次口径修订——「失败测试与本次改动是否同源」原本被留给模型，而它本来是路径上算得出来的结构性事实；把它交给模型之后，同一个案例三次里出现了两种都"讲得通"的答案。

## §6 验收（未来，不是本轮）

指标（按重要性）：

1. **引用可核验率**：每条引用都能在材料原文找到（目标 100%，硬门槛）；
2. **零越权**：改变规则分支 / 因果断言 / 材料外事实的条数（目标 0）；
3. **fail-closed 覆盖率**：注入超时、格式错、模型不可用时，回退到原行为的比例（目标 100%）；
4. **人的判断**：建议是否真的缩短了定位时间（人评，样本外）；
5. **无价值建议占比**：不能为了「有输出」而输出。

**不采用**：分类准确率作为主指标。

## §10 正式边界裁决（2026-10-17，Human 裁决）

**状态：设计与契约已冻结，实现未开始。这里停在「实现前审阅点」。**

本节的每一条都是 Human 在 2026-10-17 的明确裁决；§7 的未决项在这里被部分关闭、部分继续挂着（见 §10.7）。**本节不含接口、不含代码、不改任何现有行为。**

### 10.1 裁决一：消息形状 —— 同一条通知 + 可选的模型补充

**裁决**：同一条消息。主体是现有的 CI 失败通知，**只有**模型给出通过校验的补充时，才在其后追加一段「补充复查建议」。**不做第二条消息**（第二套生命周期）**也不把补充拼进主句**（读的人分不清哪句是规则判断、哪句是模型补充）。

**四条不变量**（任何一条被打破即视为越界）：

1. **一次失败最多一次通知**——模型补充不新增通知，`repository-ci-attention.delivered` 的语义、去重与计数一个字不改；
2. **模型不决定投递**——它只在内容上补一句；投不投、投什么形状，仍由 `repository-ci-attention` 决定；
3. **模型失败不改变原有行为**——超时 / 格式错 / 引用对不上 / 不可用，一律回退到今天的普通通知，**一字不差**；
4. **事实史里只有投递事实**——不新增事实 kind、不写 chronicle（沿用 §4 的结论）。

**补充段必须自带身份声明**（裁决原句：读的人分不清，边界就只存在于代码里）。补充段固定以：

```text
补充复查建议（模型，不是规则判断）：
```

开头，且必须**在内容最前面**，不得埋在段尾。

### 10.2 裁决二：只开放 `commit-comparison-indeterminate`

| `missing` 取值 | 是否允许补位 | 理由 |
| --- | --- | --- |
| `commit-comparison-indeterminate` | **允许** | 材料最全（run、jobs、日志、diff、历史都在），只是「同源判定」做不出来；这是材料够、规则认输的地方，也是三轮实验里被判据缺陷坑过的地方（§2.11） |
| `relevance-not-established` | 不允许 | 相关都没建立，给的是**软建议**——最容易产出「看着像真的、其实没有依据链」的补位，今天的通知已经诚实 |
| `no-github-ci-facet` | **不允许，而且今天到不了** | 措辞要准确：`src/repository-ci-attention/plugin.ts:218-219` 在 facet 不可用时**直接 return**，根本不会走到诊断 owner，模型更没有机会被调用——它是「到不了」，不是「被模型拒绝」 |

**扩张条件**：只有当这一支站稳（引用可核验率 100%、零越权、fail-closed 覆盖 100%、真机材料上确实缩短定位时间）之后，才讨论是否放开另外两支。**扩张不是默认方向。**

### 10.3 裁决三：时间预算与取消语义

**参数形状**（显式配置纪律，与 `--proactive-ci-delay-ms` 同源）：

- `--proactive-ci-supplement`：开启模型补充（opt-in）。要求同时具备已有的 CI 范围与模型端点；**不给它一个隐含的开关默认值**。
- `--proactive-ci-supplement-budget-ms <integer>`：与它**成对必填**，校验区间 30 000–600 000。

**没有插件默认值**。理由与 `src/repository-ci-attention/plugin.ts:60-62` 对节奏的同一条判断一致：

> `Explicit by design… a default cadence would be this plugin deciding how often Hikari looks at a repository.`

「Hikari 愿意为一句补充等多久」同样是操作者的策略，不是插件的默认值。

**首轮推荐值：180 000 ms。身份要说准确**：

- 它是**首轮推荐值**，不是插件默认值（不指定就不启动补充）；
- 它**不是**经产品路径验证的正式最优值；
- 它是按 §2.10/§2.11 那批**可行性探针**的 9 次实测选的：中位数 87 秒、最长 170 秒，180 秒覆盖 9/9、给最长观测留 10 秒余量。**它不是能覆盖这些样本的最小整数秒数**，只是「不会把补充做成装饰品」的一个有据可依的起点。
- **复核条件**：首次接入真实产品路径后，记录每次调用的实际耗时分布；按新分布重新决定这个值。**复核之前，它只是起点。**

**取消语义必须两分**（这是本裁决里最容易含混的一条）：

| 问题 | 含义 | 谁负责 |
| --- | --- | --- |
| 客户端取消 | Hikari 不再等这条回答，继续投递原始通知 | 我们（`AbortController`） |
| 服务端推理终止 | 推理服务不再为这条已放弃的请求消耗算力 | 推理服务（断连取消是否生效，不由我们单方面推导） |

**第一条是投递可靠性的必要条件；第二条关系到长跑之后是否积累无用推理任务。**验收里**不得**用客户端超时测试代替服务端取消的证据；推理服务不支持时，必须**写明「不支持，未验证」**，而不是默认它取消了。

**周期界（措辞要精确，不要写成无条件的硬上限）**：

```text
正常完成或超时的情况下：  T_cycle ≤ B + D + T_o
```

其中 `B` 是模型等待预算、`D` 是 `--proactive-ci-delay-ms`、`T_o` 是其余观察 / 日志 / 投递 / 调度耗时。**这个上界成立的前提是「模型等待确实有界，且取消后的清理也能结束」**——所以在验收里它是一个**带容差的测量关系**，不是一个可以写成硬编码断言的不变式：

- 分别记录三个时间戳：**模型等待时间**、**通知完成时间**、**下一轮启动时间**；
- 断言用「≤ B + 小容差」而不是精确值；
- 若取消后的清理不结束（例如连接池不释放），这个上界就不成立——那正是要测出来的东西。

**已知代价，必须写下来**：在 `commit-comparison-indeterminate` 这一支上，人第一次看到失败通知**最多会比今天晚约 3 分钟**（`B` + `D` + `T_o`）。这是「一条消息」的必付成本，**不是性能退化**；将来若有人把它当 bug 修，修法恰好是拆成两条消息——那才是真正的破坏。

### 10.4 裁决四：可观测性（日志，不进事实史）

模型行为**不写 chronicle、不加事实 kind**（模型行为不是领域事实），但必须有**固定前缀的日志**，因为失败分支今天会安静地消失——`src/repository-ci-attention/plugin.ts:304` 的外层 `catch` 会吞掉整轮，这个坑我们花过一整天。

最小集合（前缀固定、可直接 grep）：

```text
模型补充：已附加（<耗时> ms）
模型补充：超时（<B> ms）→ 未附加
模型补充：格式不合 → 未附加
模型补充：引用不可核验（<n> 条）→ 未附加
模型补充：端点不可用 → 未附加
```

无价值 / 未触发时不打日志（避免噪声）。

### 10.5 裁决五：验收（两段，第二段不许自欺）

**A 段「不添乱」（fail-closed）**——这是实现前必须先过的段：

| 场景 | 期望 |
| --- | --- |
| 允许分支 + 有效补充 | 一条消息，正文含补充段；`delivered` 计数 1 |
| 允许分支 + 格式不合 | 一条消息，**无**补充段；计数 1 |
| 允许分支 + 引用不在材料里 | 一条消息，**无**补充段；计数 1（并记「引用不可核验」日志） |
| 允许分支 + 超时 | 一条消息，**无**补充段；计数 1 |
| 允许分支 + 端点不可用 | 一条消息，**无**补充段；计数 1 |
| 另外两个 `missing` | **不调用模型**；一条消息；计数 1 |
| 同一 run 再次出现 | **不投递**（去重语义不变） |

**关键断言**：模型调用失败与模型成功但建议被拒，**都不得改变 `repository-ci-attention.delivered` 的语义**——这是内容生成失败，不是投递失败。

**超时测试要分开测两件事**：

1. **客户端**：假端点 `sleep ≥ 300 s` → 投递仍在 `B` + 小容差内完成、计数 1、下一轮正常排上（证明「模型拖不死 Hikari」）；
2. **服务端**（若推理服务支持断连取消）：确认取消信号确实终止了服务端推理；**同时在长跑场景确认不会因旧请求未结束而无限积累模型请求**。推理服务不支持时，如实写「未验证」。

**B 段「有价值」**——用真实材料，不用第四轮人造案例：

材料是 main 上那五个**真红 run**（对应提交 `dc62a23`、`7d9fade`、`febbf15`、`dee5659`、`8b74005`，都由真机 `act` 推上去、都是被看见的失败）。要问的是：**接上真实 Strata 模型之后，原来的确定性系统是否仍然可靠，模型补充是否真的值得这份等待成本。**

**这一段有一个必须写明的限制**：如果**用这五个案例反复调提示词**，再用它们证明最终效果，**就不是独立验证**。所以：

- 允许拿它们**调**（这是开发输入）；
- **调过之后必须换材料复测**（新的真红 run、或留出不看的那几个），否则结果只能写成「在同批材料上可用」，不能写成「模型帮得上忙」；
- 这一条**写进验收记录**，不是写在脚注里。

### 10.8 裁决七：材料采集 —— 3 个请求，第三个要凭据（2026-10-17 追加，同日修订，Human 裁决）

**决定**：只在 `commit-comparison-indeterminate` 这一支、且只在真正要调用模型之前，采三样：

| 请求 | 拿到什么 | 匿名可用？ | 不拿会怎样 |
| --- | --- | --- | --- |
| `/repos/{o}/{r}/commits/{head_sha}` | 改动文件清单 + 每文件 `patch` | **是**（实测 200） | 说不出「这个文件改了什么」，只能复述代码已算出的对应关系 |
| `/repos/{o}/{r}/actions/runs/{id}/jobs` | 哪一步失败、步骤结论 | **是**（实测 200） | 说不出「先看哪一步」 |
| `/repos/{o}/{r}/actions/jobs/{job_id}/logs` | 失败步骤截至失败点的日志片段 | **否**（见下） | 说不出失败的是哪个测试、断言比较的是什么 |

**为什么这不再是「渲染已有数据」**：今天的采集只拿 run 本身——`src/github-ci/github.ts:100` 发 `/repos/{owner}/{name}`，`:109` 发 `/repos/{owner}/{name}/actions/runs?per_page=1`。jobs / steps / 日志 / diff，产品侧一个都没有；§5 那张材料表是**新增采集**。

**边框被正面撞破了（2026-10-17 同日修订）**：`src/github-ci/github.ts:28-30` 的原注释是——

> an unauthenticated caller shares a quota of 60 requests per hour per address, and one observation spends two. A caller that needs more is a caller that needs a credential, and a credential is a decision this slice does not make.

上一版裁决写的是「仍不引入凭据」。**同一天它被实测推翻了**：

- `GET /repos/{o}/{r}/actions/jobs/{job_id}/logs` 匿名 → **HTTP 403 `Must have admin rights to Repository.`**
- 同一个 403 在 `microsoft/TypeScript` 这种大公开仓库上完全一样 → **不是本仓库特殊，是这一类资源的口径**（`/actions/runs/{id}/logs` 同理）；`/actions/runs/{id}/jobs` 与 `/repos/{o}/{r}/commits/{sha}` 匿名仍 200。

所以第三条材料不是「多花一点配额」，而是**要求仓库 admin 级权限**。**Human 裁决：引入这枚凭据，越过这条边界。**

这里要写清的正是那句「不悄悄发生」：`github.ts:28-30` 说的是「凭据是这一片不做决定的事」，现在这一片**做了这个决定**，并把它记在这里，而不是让一枚 token 从某个环境变量里溜进代码。

**凭据契约（实现评审逐条对）**：

1. **形态**：CLI 参数 `--github-token-env <ENV_NAME>`，只从环境变量读；不读配置文件、不读 `git credential` helper、不落盘、不写 Chronicle。
2. **最小权限**：先试 fine-grained PAT **只给 `Actions: read`**；只有实测不够才退到 classic `repo`。今天的 403 是**匿名视角**——换成 token 后到底只需要什么权限，没有任何人验证过，这条必须用真 token 实测一次再写死。
3. **观察也带这枚 token（我的理解，若与你的本意不符就改回匿名观察）**：匿名额度 60 请求/小时、一次观察花两个（`src/github-ci/github.ts:28-30`）——`D = 30 s` 时是 120 观察/小时，**必然耗尽**，而耗尽的表现是 `githubCi` facet `unavailable` → attention 整轮沉默（真机上反复撞到）。同一枚 token 顺带把这条命门解掉，否则我们会保有一枚 admin 凭据，却继续被 60/h 掐住。
4. **失败语义**：token 缺失 / 无效 / 限流 → 材料请求失败 → **整条补充回退**（fail-closed），日志一行；观察若带 token 失败则**退回匿名观察**，不因此沉默。
5. **安全清单**：token 只出现在 `Authorization` 请求头；不进日志（日志只记「有 / 无凭据」）；不进材料（模型永远看不到它）；不进错误消息；不出现在任何提交、文档示例或 `current-stage` 记录里。
6. **已知风险（写出来，不假装消失）**：
   - 这枚 token 能拿到的权限比匿名大一个量级，泄露面随之变大；它是本片**唯一**新增的高权限物件。
   - 日志是**攻击者可影响的内容**（仓库里的代码能打印任意文本），现在它会被送进模型。缓解：模型没有任何工具权限、输出必须带材料内逐字引用（不可核验即回退）、结构不合即回退、补充段自带身份声明。**残留风险承认存在**，不声称已消除。

**未验证，进实现评审**：token 下的最小权限集合；token 下的限流头；`/actions/jobs/{id}/logs` 在 token 下真实返回什么（302 跳 zip / `text/plain` / 其它）——今天的 `getJson()`（`src/github-ci/github.ts:39-67`）只装 JSON。

**一个被消掉的二选一**：`GET /repos/{o}/{r}/commits/{sha}` 一次返回 `files[]`，每项同时带 `filename`、`additions`、`deletions`、`patch`——**「清单」与「内容」是同一个请求**，差异只在 token 与截断。§7 第 3 项的「清单还是 diff」本身是个假二选一；真正的取舍是「要不要再花两个请求拿 jobs 与日志」，本轮的回答是要。

**截断规则（写进契约，不给模型挑）**：

- `patch`：只送**对应关系命中的文件**（通常 1–2 个），每文件 ≤ 200 行、合计 ≤ 400 行，超出标 `…（已截断）`；
- 日志：只送**失败步骤截至失败点**的片段，≤ 200 行；二进制与生成物（如 `package-lock.json`）按扩展名跳过，并**注明「已跳过」**——「没送」不能被读成「不存在」；
- 任一请求失败或限流 → **整条补充回退**（fail-closed），不重试、不降级成半个材料。半个材料比没有材料更危险（§2.11 的教训：材料薄不会让模型更谨慎，只会让它更含糊）。

**已知局限（不假装）**：

1. `/commits/{head_sha}` 只覆盖**那一个提交**的改动；一次 push 带多个提交时，材料只覆盖最后一个。v0 用这个口径，不宣称它等于「本次 push 的全部改动」。
2. 第三条的响应形状在拿到真 token 之前**不确定**（见上「未验证」）。实现评审的第一件事是把它测出来，再决定解析路径——本节不替它猜。

### 10.9 裁决八：连续失败不建退避（2026-10-17 追加，Human 裁决）

**决定**：v0 不退避。加可观测性，并预先写死复访触发条件。

三条理由：

1. **伤害有界、不累积**：`src/repository-ci-attention/plugin.ts:221` 的 `detectNewFailure` 每周期只拿**最新那一次 run** 判一次，所以一个周期最多一次模型调用。端点抽风时，代价是「这一轮变成 B + D」——不排队、不堆积、不丢消息。
2. **最常见的失败不贵**：连接拒绝是毫秒级失败；真正吃满预算的只有「连上了但不回话」这一种。
3. **退避会引入更难解释的隐性状态**：「模型明明恢复了，却因为我刚才失败过所以不再尝试」。这句话在评审里没法一句讲清，而它要解决的问题（周期从 30 秒拉到 3.5 分钟）本身不致命。

**复访触发条件（写死）**：真机观察中出现**连续 ≥ 2 次超时**，就把「按时间冷却、自恢复」的退避作为下一条小改动补上。现在不先建一个没有证据的状态机。

**失败一律不改变投递**：超时 / 格式错 / 引用不可核验 / 端点不可用，都走原行为，通知计数仍为 1（§10.1 不变量 3）。

- 不写实现、不接 `--model-endpoint`、不新增 CLI 参数（本节只是在**定义**它们——包括 §10.8 的 `--github-token-env`）；
- 不改 `src/repository-ci-diagnosis-proposal/judgement.ts`；
- 不新增插件 / service / 事实 kind；
- 不把模型输出写进 chronicle 或执行器；
- 不因为拿了 token 就顺手做**别的** GitHub 写操作：凭据只用于 §10.8 那三个只读请求（外加观察），不发 POST/PATCH/DELETE，不代表获得「能改远端」的能力；
- 不承诺「模型能给出有用建议」——那正是 B 段要验的东西。

## §11 实现评审的硬边界与议程（2026-10-17，Human 裁决）

> 本节是 §10 之后 Human 就「谁采材料、失败怎么分类」下的裁决。**仍然只有文档，没有产品代码。**

### 11.1 材料采集归 `github-ci`（不新建 owner）

三段职责一句话一个：

| owner | 只负责 |
| --- | --- |
| `github-ci` | **唯一**的 GitHub API 访问者：凭据、请求额度、响应获取、有界材料（run / jobs / steps / 日志 / diff） |
| `repository-ci-diagnosis-proposal` | 消费**已经获取并整理好**的有界材料，产出受约束的候选补充 |
| `repository-ci-attention` | **唯一**的轮询、去重、投递与回执写作者 |

由此三条禁止：

- 模型补充模块**不持有** GitHub token；
- 它**不发**任何 HTTP 请求，也**不下载**日志；
- 不新开第二个采集 owner、不新建第二个投递者、不新建「补充专用」的回执事实族。

**一条必须写死的实现约束（Human 原话的直接推论）**：

> 不要因为日志读取失败，就把本来已经成立的 CI 失败事实也判成不可用。日志是补充诊断材料，不应反过来成为原始通知的前置依赖。

也就是说：观察（run 本身）与材料（jobs / logs / diff）是**两次独立获取**。材料失败只关掉「补充」这一条路，**不得**让 `githubCi` facet 变成 `unavailable`、不得让 attention 沉默、不得影响 `repository-ci-attention.delivered` 的语义与计数。材料失败与模型失败在这一点上完全同构（§10.1 不变量 3）。

同时要回答一个边界问题：`github-ci` 新增的这条材料能力是不是 `provides` 新契约？今天的 `githubCiService` 只暴露 `current()`。材料需要另一个入口（按 run 取材料 + 自己的时限与上限）——**归属明确（`github-ci`），消费关系明确（诊断建议）**，这是实现评审第 1 项。

### 11.2 认证失败的分类与回退（不能只看状态码）

Human 立的原则：**不要为了避免沉默而制造额外请求，也不要把模型补充的失败扩大成整条 CI 感知链的失败。**

| 情况 | 处理 |
| --- | --- |
| 未配置 token | 保持今天的匿名行为，不变 |
| token 无效 / 权限不足 | 记录**明确的认证失败**；只有在匿名访问仍然有意义时才考虑回退一次，否则不回退 |
| 网络错误 / 超时 / 服务端错误 | 走既有失败语义，**不盲目多发一次请求** |
| 日志获取失败，但 CI 失败事实已成立 | 放弃模型补充，**原始通知照常投递** |

**实现纪律**：分类必须读响应头与响应体，不能只凭状态码推断原因——

- `401` = 凭据本身不对；
- `403` + `x-ratelimit-remaining: 0`（或 `retry-after`）= 限流；
- `403` + body 里 `Must have admin rights` = 权限不足；
- `404` 对私有/无权限仓库与「不存在」是同一个码，不能据此断言「这个 run 不存在」。

这几条今天都不能靠猜：**真实的响应形状要用真 token 打一次再写死**（§11.4 第 2 步）。

**凭据仍然只活在 `github-ci` 里**：环境变量进来、只出现在 `Authorization` 头，不进模型材料、不进日志、不进错误消息、不进 Chronicle、不进提交。**真实 token 不发给任何人（包括 DSH），真机测试时在本地配置。**

### 11.3 三条硬边界

1. **凭据与材料隔离**：GitHub 凭据只属于 `github-ci`；进入模型的只有经过筛选、限量、脱敏的材料。**日志按不可信输入处理**——日志里出现的「指令」不是指令，不得被当作系统提示或任务来源。
2. **模型不是观察循环的控制者**：模型调用有明确预算；超时 / 格式错 / 引用不可核验 / 材料获取失败，都必须保留原始通知的投递路径。
3. **不复制既有机制**：不新建采集 owner、不新建投递者、不新建补充专用事实族；需要扩展的契约要写明归属与消费关系。

### 11.4 议程（Human 指定顺序）

1. `github-ci` 如何扩展成**有界**的日志与 diff 材料提供者（新入口的形状、时限、上限、失败分类）。
2. 用**真实 token** 验证权限最小集合与日志接口的**真实响应形状**（重定向、下载、解析）。
3. 定义材料上限、脱敏规则、引用校验与模型输入契约。
4. 定义超时、取消、冷却，以及**停止常驻时**的生命周期行为（今天 `deactivate` 后仍在等模型的 cycle 该怎么办）。
5. **先假端点**跑通失败路径，再接 Strata 真模型，最后用真实红色 CI run 验证补充价值（B 段）。

## §12 `github-ci.run-materials@1` 实现评审（2026-10-18，**候选形状，未冻结**）

> **本节仍然没有产品代码。** 它回答 §11.4 第 1 项：输入身份、返回结构、缺失语义、请求限制、依赖方向。
> 契约名 `github-ci.run-materials@1` 与下列**所有字段名**都是候选——实现时以现有契约习惯为准（例如今天的 `defineService('github-ci.current', 1)` 就只用了 `current`）。**不候选的是 §12.1–§12.4 的语义**：那五条是这一节的正文，改名可以，改语义要重开评审。

### 12.1 输入身份：材料绑在「已经观测到的那一条 run」上，不是「再查一次最新」

```ts
interface GitHubCiRunMaterialsRequest {
  readonly repository: string; // GitHub 报的拼写（`observation.repository`），不是配置里写的
  readonly runId: number;      // 正整数
  readonly headSha: string;    // /^[0-9a-f]{40}$/
}
```

四条规则：

1. **仓库只认一个。** `repository` 与插件配置的 `owner/name` **大小写不敏感相等**才继续；不等就拒绝（抛，不查、不猜）。理由与 `src/github-ci/github.ts:77-82` 那段注释同一条：配置是「怎么称呼一个仓库」，观测是「这个称呼指到了哪个仓库」；材料只能发给**这一个**。
2. **URL 只由校验过的输入拼。** 三个字段都过形状检查后拼进固定模板；**不接受**路径片段、不接受完整 URL、不接受第二个仓库、不接受分支名或 `?` 参数。这就是「不开放任意 URL / 任意仓库」的实现形态——不是加一个白名单，而是根本没有可以把 URL 塞进去的参数。
3. **身份确认不靠「再读最新 run」，靠回包自证。** 请求的是 `/actions/runs/{runId}/jobs`，GitHub 的 job 对象自带 `run_id` 与 `head_sha`；回来的 `head_sha` 与请求里的**逐字不等**，整份材料就返回 `identity: 'mismatch'` 且**不带任何内容**。这样「再读一次、悄悄换了条 run」在结构上不可能发生——它没有可换的对象，只有被点名的那个 id。
4. **「还没有」不当「没有」。** run 已排队但尚无 job 时，`jobs` 返回 `pending`，不返回 `missing`。今天的 `types.ts:15-18` 对 `conclusion` 立过同一条规矩：GitHub 合法地说「还没有」，与「这次没读到」是两件事，合并成一个值就是丢信息。

### 12.2 返回结构：每份材料各自带「有没有 / 为什么没有」

```ts
type GitHubCiMaterialGap =
  | 'not-found'        // 404：对私有/无权限仓库与「不存在」同码，见 `github.ts:165-169`
  | 'authentication'   // 401；或 403 且响应体是权限类
  | 'rate-limited'     // 403 + `x-ratelimit-remaining: 0`，或带 `retry-after`
  | 'transport'        // 连接失败 / DNS / TLS
  | 'timeout'
  | 'unusable-answer'; // 非 JSON、形状不对、重定向到非预期目标

type GitHubCiMaterial<T> =
  | { readonly kind: 'present'; readonly value: T }
  | { readonly kind: 'missing'; readonly reason: GitHubCiMaterialGap }
  | { readonly kind: 'pending' }; // 只对 `jobs` 有意义：run 还没有 job

interface GitHubCiRunMaterials {
  readonly requestedAt: string;
  readonly repository: string;              // GitHub 的规范拼写
  readonly runId: number;
  readonly headSha: string;                 // 回包自证的那个
  readonly identity: 'confirmed' | 'mismatch';
  readonly jobs: GitHubCiMaterial<readonly GitHubCiJobMaterial[]>;
  readonly changedFiles: GitHubCiMaterial<GitHubCiChangedFiles>;
  readonly log: GitHubCiMaterial<GitHubCiLogExcerpt>;
}
```

三条规则：

1. **三份材料彼此独立。** 日志没拿到不等于 diff 没拿到；一个 `missing` 不牵连另外两个字段。**「整条回退」是消费侧的资格规则（§10.8），不是提供侧的返回值语义**——提供侧只负责把「这份没拿到、因为什么」如实交出去。
2. **截断是「在场」的一种属性，不是缺失。** `GitHubCiLogExcerpt` 带 `{ kind: 'cut'; droppedBytes: number }`；`GitHubCiChangedFiles` 带 `skipped: readonly { filename: string; why: 'binary' | 'generated' | 'over-limit' }[]`。§10.8 那句「没送不能被读成不存在」在这里变成一个字段，而不是一句注释。
3. **提供侧不判断「够不够」。** 哪些缺口使补充失去资格，由 §10 已冻结的补充契约决定（见 §12.8 的 Q2）。`github-ci` 不知道诊断是什么，这一条与 §11.1「材料采集归 `github-ci`，不负责决定材料对诊断有没有价值」是同一句话的两种写法。

### 12.3 请求、上限与时限

| 项 | 值 | 依据 |
| --- | --- | --- |
| 请求数 | **3**，顺序发、不并发 | §10.8 裁决 |
| 单请求超时 | 10 000 ms | 沿用 `src/github-ci/github.ts:7` 的 `ACQUISITION_TIMEOUT_MS` |
| **材料总时限** | **20 000 ms**（含重定向） | 补充预算 180 s，材料不许吃掉超过约 1/9；超了就是整份超时，不是半个 |
| `jobs` JSON 体积 | ≤ 1 MiB | 只需要 name / conclusion / steps 的 conclusion，超了就是 `unusable-answer` |
| `patch` | ≤ 20 文件；每文件 ≤ 200 行；合计 ≤ 400 行 | §10.8 截断规则 |
| 日志 | **最多读 64 KiB**；流式读取到上限即断，**不先整份下载再截**；**保留哪一段按失败步骤的边界切，不简单取尾部** | 实测尾部是收尾噪音（§12.11 第 3 条）；先全下再截会让「有界」只体现在内存里 |
| 重试 | **不重试** | §10.8 fail-closed |

一条实现细节值得写在这里，因为它是「有界」和「假装有界」的分界：日志响应是 `text/plain`（重定向到临时地址），必须走**流式读取 + 字节计数 + 主动 abort**；`getJson()`（`src/github-ci/github.ts:39-67`）装不下它，材料入口需要自己的读取器，而不是给 `getJson` 加一个 `text` 开关。另外两条已实测（§12.11）：日志里**有 ANSI 转义**，送模型前必须剥；首跳是 **302 到 Azure Blob 的签名地址**，签名地址自认证，token 不需要跟着跳转。

### 12.4 失败语义：两次独立获取，材料永不改写观察

- **per-material 的失败是值，不是异常。** 只有「拒绝按你要求的做」才抛（仓库与配置不符、`runId` / `headSha` 形状不对）——与 `src/github-ci/errors.ts` 今天的两分法一致：`GitHubCiError` 是「我拒绝」，`GitHubCiObservationError` 是「试过了没拿到」。材料把后者降级成 `missing`，因为**它必须能被消费侧当成一个可以据以决定「本次不附加」的值**，而不是一个需要 catch 的意外。
- **材料在没有观察的情况下不许被调用。** 它的输入（`repository` / `runId` / `headSha`）全部来自一条**已经成立**的 observation；调用方拿不出这三个值就说明它没有失败事实可讲。
- **材料不写 Chronicle、不写事实、不产生 `delivered`。** 与 §10.4「模型行为不是领域事实」同一条理由——采集行为也不是。
- **材料失败不改变观测。** 观察与材料是两次独立获取（§11.1）；材料层没有任何路径能改 `GitHubCiObservation`，因为它拿不到那个对象。

### 12.5 依赖方向：三个候选，推荐第三个

这是本节唯一真正有争议的地方，因为用户原话是「消费方 = `repository-ci-diagnosis-proposal`」，而今天的 `src/repository-ci-diagnosis-proposal/contracts.ts` 写着两句话，正对着这条：

> It does **not** acquire a world snapshot: the assessment comes in with the request, which is what keeps one cycle to one acquirement.
> A dependency that rejects makes this reject: `insufficient-evidence` is an answer this layer reached from material it had, and a failed acquisition is a question it did not get to put.

**候选 1（用户提案的字面形态）**：诊断 `requires` 材料服务，自己在 `indeterminate` 那支去取。
- 优点：与「由诊断路径决定何时需要补充」字面一致；少一层。
- 代价一：诊断从「材料随请求传进来的函数」变成「自己取材料的模块」，`contracts.ts` 那两句要重写。
- 代价二（更硬）：诊断一旦因取材料而 reject，attention 的 cycle catch（`src/repository-ci-attention/plugin.ts:304`）会吞掉整轮——**这正是 §11.1 明令禁止的「材料失败让原始通知静默」**。要在候选 1 里避免它，得再给诊断加一条「材料失败必须吞掉」的纪律，而那条纪律与它自己写的「依赖 reject 就 reject」互相矛盾。

**候选 2**：attention 取材料，随请求传进诊断。
- 优点：诊断保持纯；材料失败天然只影响补充。
- 代价：感知插件开始组装领域输入（它要知道「材料」这个概念），attention 的职责从投递扩成了装配。

**候选 3（推荐）**：**补充模块**取材料，诊断一行不动。
- 链路：attention 拿到 `insufficient-evidence('commit-comparison-indeterminate')` —— 这是**确定性诊断自己给出的判断结果**，不是世界事实（术语按 Human 2026-10-18 的纠正改；它可以当「进入补充路径的条件」，但不得在契约里被写成事实）—— 进补充模块 → 补充模块 `requires` 材料服务 → 取材料 → 按**冻结的**补充契约判资格 → 调模型 → 校验引用 → 交回补充段或 `undefined`。
- 为什么是它：**唯一真正需要材料内容的模块就是补充模块**；它需要的三个输入全在 occurrence 里；诊断保持「材料随请求传入」，`contracts.ts` 一个字不用改；attention 只多一个按枚举值分派的分支，那不是判断。
- 对 §11.1 三条禁止逐条对：不持有 token（token 在 `github-ci`）✓；不发请求、不下日志（它调契约，`github-ci` 发）✓；不新开采集 owner / 投递者 / 事实族 ✓。
- 残留代价：补充模块因此成为「材料 + 模型」两个外部依赖的持有者，它的失败面比原设计大一点点——但那正是它该负责的面。

**已裁（2026-10-18）：采用候选 3。** 连带冻结两条失败隔离约束（§12.8 Q1），其中第二条落在 attention 上——候选 3 单独不足以挡住「静默」回潮，必须由调用方再设一道局部失败边界。

### 12.6 采集侧**不算**对应关系

§5 说「能用代码算出来的关系，不交给模型推断」，并把「失败测试文件 ↔ 改动文件 ↔ 共享路径段」列在材料里。这里要划一条更细的线：**那套对应关系由诊断侧算，不由 `github-ci` 算。**

`github-ci` 交出去的是「哪些文件改了、每个改了什么」与「哪个 job / step 失败了」——两条来源各自的原文。把二者对起来（哪个测试名出现在哪个文件名里、共享哪段路径）是一个**关于两个来源的判断**，而 `src/github-ci/types.ts:1-4` 那段开篇注释已经立过规矩：一个来源不做「两个来源说的是不是同一件事」的判断。这条线不划清，材料契约会顺手长成「通用 GitHub 分析器」。

### 12.7 真 token 阶段要验证什么（清单；执行顺序见 §12.9）

按 Human 指定的四问，加一条兜底：

1. **最小权限**：fine-grained PAT 只给 `Actions: read` 是否足以读 `/actions/jobs/{id}/logs`（今天的 403 是匿名视角，换 token 后需要什么**没有任何人验证过**）。
2. **真实响应形状**：`/actions/jobs/{id}/logs` 到底是 `302` 到临时地址后的 `text/plain`、还是 zip 流、还是别的；重定向怎么跟、要不要保留 `Authorization`、下载到多大。
3. **两次获取是否独立**：把材料请求打成必失败（关代理 / 假 base URL），确认 observation 照常成立、attention 照常投递。
4. **凭据是否始终在边界内**：token 不进日志、不进材料、不进模型输入、不进错误消息、不进 Chronicle、不进提交。
5. **兜底**：如果真实服务的**断连取消**能力无法确认，按 §10.3 记「未验证」，**不拿客户端超时冒充服务端取消证据**。

### 12.8 三项裁决（2026-10-18，Human 已裁，冻结）

**Q1 依赖方向 —— 采用候选 3（补充模块取材料，确定性诊断不动），并连带冻结两条失败隔离约束。**

依赖关系：

```text
repository-ci-attention         唯一轮询、去重、投递、写回执
        │
        ├── repository-ci-diagnosis-proposal   确定性判断，保持不变
        │
        └── 模型补充模块                       按指定 run 取材料 → 判资格 → 调模型
                    │
                    └── github-ci（run-materials）  唯一 GitHub 访问者
        ↓
   原通知 + 可选补充 → 唯一投递路径（仍是 attention）
```

- **隔离约束一（补充模块内）**：取材料失败、超时、材料不合格、模型调用失败，**都不得让异常穿透到 attention 的整轮执行路径**——一律转换成可观察的「不附加补充」结果。
- **隔离约束二（attention 内）**：attention 在投递前，对**整段可选补充调用**再设一道局部失败边界。即使补充模块发生未预期异常，也**不得跳过原始通知**：记录错误后继续投递。这不是「把所有异常静默吞掉」，而是**把错误记录与原始通知的交付解耦**——两件事各有各的去处，谁都不许拖着对方一起失败。

**术语纠正（写进契约）**：`insufficient-evidence('commit-comparison-indeterminate')` 是**确定性诊断的判断结果**，不是世界事实。它可以作为「进入补充路径的条件」，但不得在契约里被定义为事实。

**Q2 资格规则 —— 采用「`jobs` + `changedFiles` 均在场且可用即可尝试；`log` 缺失本身不否决」。**

| 材料情况 | 是否允许尝试模型补充 |
| --- | --- |
| 身份核验不匹配（`identity: 'mismatch'`） | **不允许**，整份材料不进入模型 |
| `jobs` 缺失、不可解析或不可用 | **不允许** |
| `changedFiles` 缺失或不可用 | **不允许** |
| `jobs`、`changedFiles` 可用，`log` 缺失 | 允许，但**必须明确告知模型「日志未提供」** |
| 日志被截断 | 允许，保留截断标记与可核验的来源信息 |
| 历史尝试缺失 | 不单独否决，**明确标记历史材料缺失** |
| 材料获取超时或整体预算耗尽 | **不允许**，原通知照常投递 |

两条口径：

- **「在场」= 成功取得并通过结构校验**，不是「字段存在」。`changedFiles` 成功读取后**确实返回空列表**，那是一个真实的空结果，不能与读取失败混为一谈。
- **模型只能引用实际交给它的材料**：没有日志就不能声称读过日志，没有历史就不能声称历史证明了什么。**材料越薄，允许提出的补充就越有限。**

归属不变：**资格规则属于模型补充契约，不属于 `github-ci`**——提供方只报告材料及其状态，消费方决定是否有资格继续。

**Q3 `pending` —— 本次不附加，不等待第二轮。**

run 仍在排队、尚未产生 job 时：不继续等待 jobs、不调用模型、不改变原有通知内容、不增加第二次投递也不绕过既有去重；**明确记录本次材料处于 `pending`**，不误记为 `missing` 或模型失败。

接受的代价：本次通知可能没有模型补充，即使稍后 jobs 已经产生。再等一轮会引入**第二个等待点**，破坏 §10.3 已冻结的单点预算。`pending` 本身**不触发模型失败冷却**——模型根本没有被调用。

### 12.9 三项裁决之后：真 token 验证的顺序（§11.4 第 2 步）

1. 本机配置 fine-grained PAT，先验证**最小权限**能否读取目标仓库的 Actions 数据；
2. 验证 `jobs` 与**日志接口的真实响应形状**，含重定向、下载与流式读取上限；
3. 分别验证**认证失败 / 限流 / 网络错误 / 日志读取失败**四类语义；
4. 确认材料读取失败**不改变已成立的 CI 失败事实**，也不让原始通知沉默；
5. 单独验证**客户端取消**，以及**服务端是否真正停止推理**；无法确认就明确记「未验证」，不拿客户端超时冒充。

**凭据纪律不变**：token 不进聊天、不进 DSH、不进日志 / 材料 / 异常文本 / 事实记录 / 提交；执行脚本按**环境变量名**参数化，不读死变量名。

### 12.10 匿名对照已经跑过一轮（2026-10-18，无 token）

在等本机凭据之前，先用匿名请求把**不依赖 token 的那几条**打了一遍（探针 `%TEMP%\hikari-token-probe\probe.mjs`，只读、不落 token）：

1. **`GET /actions/runs/{run_id}/jobs` → 200，`jobs=2`，每个 job 确实带 `run_id` 与 `head_sha`。**
   ⇒ §12.1 规则 3 的「回包自证」**可行**，身份核验不需要第 4 个请求。这条从设计假设变成实测。
2. **同一个 job 的日志 → 403，且响应体是 JSON**（`{"message":"Must have admin rights to Repository.",…}`），**不是 302**。
   ⇒ 「重定向 / zip 流」这一层在匿名阶段根本到不了；它只可能在 token 有效后出现——**已经验过，见 §12.11 第 3 条**（302 到 Azure Blob 签名地址，不是 zip）。
3. **假 token → `401 Bad credentials`；不存在的 run → `404 Not Found`**，两者响应体都是 JSON，`message` 可读。
   ⇒ §11.2 的分类判据各自有着落：401 与「404 的歧义」都能区分，403 仍需读 `x-ratelimit-remaining` 与 body 才能分「限流」和「权限」。

**探针自己也踩了这个契约要防的坑**：第一版把 JSON 响应只留 400 字节前缀再解析，于是 `jobs=2` 被读成 `jobs=0`——一个「存在却报空」的假读数。这正好是 §12.2 的反面教材：**不可解析 ≠ 空结果 ≠ 缺失**，三者在类型上就必须分开，否则实现里会用一行 `catch { return [] }` 把它们重新粘在一起。

### 12.11 真 token 验证已经跑过（2026-10-18，本机 fine-grained token）

凭据放在本机用户环境变量 `HIKARI_GITHUB_TOKEN`（93 字符，fine-grained，响应里**没有 `x-oauth-scopes`**），探针只读、不落盘、不打印，输出自带泄漏自检（`%TEMP%\hikari-token-probe\probe.mjs` 查权限与形状，`probe2.mjs` 查材料内容）。

2. **diff 材料确实在一个请求里**：`GET /repos/{owner}/{repo}/commits/{sha}` → 200，`files[]` 带 `patch`（本次 1 文件、290 字符，计入 `core`）。⇒ §12.3「不做清单 / diff 二选一」成立。

   - **签名地址不带 `Authorization` 也返回 200** ⇒ token 只需发往 `api.github.com`，**不必随重定向离开认证边界**（§10.8 安全清单的直接证据）。
   - 完整日志 **140 464 B**，**含 ANSI 转义**（`\x1b[`）⇒ 送模型前必须剥色码；64 KiB 上限会截掉一半以上。
   - 末尾 6 行是 `git config` 与 `Cleaning up orphan processes`——**收尾噪音，不是失败断言** ⇒ 原先「保留尾部」的说法被实测推翻，§12.3 已改为「按失败步骤的边界切」。
4. **失败位置能在 job 里定位**：同一 run 的失败 job 的 `steps[]` 里有 `conclusion: failure` 的那一步（本次 `Build and test`）⇒ 截断的锚点应取步骤边界，而不是按字节数猜。
5. **失败分类各自有着落**：假 token `401 Bad credentials`；不存在的 run `404 Not Found`；匿名读日志 `403 Must have admin rights to Repository.`（§11.2 三分全有实测落点）。

**还没验的那一条**：§12.4 的「材料失败不影响原通知」是**产品级**性质。今天只验到 API 层（假 run 404 的同时观察仍 200）；真正的隔离要等实现落地后按 §12.8 的两道失败边界测。

**这轮探针又踩了一次 §12.2 的坑**（已修）：第一版只留 400 字节前缀再解析 JSON，把 `jobs=2` 读成 `jobs=0`——「存在却报空」的假读数，正是「不可解析 ≠ 空结果 ≠ 缺失」必须分开的原因。

### 13.4 日志（逐字，可直接 grep）

```text
模型补充：已附加（<耗时> ms）
模型补充：超时（<B> ms）→ 未附加
模型补充：格式错误 → 未附加
模型补充：格式错误（内容里出现了身份标签）→ 未附加
模型补充：引用不可核验（<n> 处）→ 未附加
模型补充：端点不可用 → 未附加
模型补充：材料读取失败（<reason>）→ 未附加
模型补充：未预期异常 → 未附加
```

前两行里，`已附加` 由 attention 写（只有它知道字有没有进消息），其余全是补充模块写；`未预期异常` 是 attention 第二道边界写的。

- 只记原因与耗时；**不记** token、提示词、材料原文、日志原文。
- 不写 chronicle、不加事实 kind、不进 `hikari status`（§10.4 的裁决没有被实现改写）。
- 「诚实的弃权」（模型自己说材料不够）**不写日志**：它不是异常，是这一支的正常出口。失败与弃权在日志里可区分，在消息里不可区分（都是只有原文）。
- `identity: 'mismatch'` **不写日志**：两个标识不等不是"材料没到"，观察侧已经报过它看到的配对；再写一行会把一件事说成两件。
- 默认 `log` 为 `undefined`（静默）。写不写由装载方决定，runner 才有 stderr。

### 13.8 两处实现偏移（已裁决，2026-10-18）

原报的两处偏移按 Human 裁决改为下面这条**唯一归属**，代码已按此实现：

1. **身份标签由代码固定，不由模型生成，也不由 language 渲染。** 常量现在只在一处：`src/repository-ci-attention/supplement-block.ts` 的 `REPOSITORY_CI_SUPPLEMENT_LABEL = '补充复查建议（模型，不是规则判断）'`。答案形状只有 `text` 与 `cited`，没有可写标签的字段；正文里只要有一行与标签逐字相同（去首尾空白后比较），**整段不附加**并写一行 `模型补充：格式错误（内容里出现了身份标签）→ 未附加`——两条标签会让「哪段来自事实、哪段由模型写」失去可读性，宁可不要。
2. **消息拼接有唯一 owner，且是 attention。** 补充模块返回的是**内容**：`RepositoryCiDiagnosisSupplementContent { text, cited }`——经过核验的文字与被核验的材料行，不带空行、不带标签、不带自身排版。attention 用 `supplementBlock(content)` 产出 `['', LABEL, ...text.split('\n')]`，这是「空行 + 固定标签 + 补充正文」的唯一写点，也是补充段进入 `delivery.deliver(lines)` 的唯一路径。
3. **由此产生的日志归属也随之改了。** `模型补充：已附加（<耗时> ms）` 由 attention 写，不再由补充模块写：只有真正把字附加进消息的那一方，才有资格说「已附加」；模块自己只写「未附加」的原因行。

验收断言同 §10.5：最终消息里必须带着这行固定标签；没有有效补充时**不出现**该标签；模型无法用任何字段覆盖它。

### 13.9 静态审查：生产组合的风险（2026-10-18）

四问逐条回答，均以源码位置为准：

1. **「加载了但没配置」是否与之前完全一致？** 是。resident 在 `repository-ci` 分支里以 `{ log }` 加载补充插件（`src/cli/resident.ts:567-572`），不给 `model`；`parseConfig` 因此返回 `{}`，`setup` 里 `model: undefined`，`attach()` 在任何材料读取**之前**返回 `undefined`（模块级用例「没配模型时什么都不读，也不问」）。消息行与这一片之前逐字相同（产品级用例「没配模型：插件照样在位，消息与这一片之前逐字相同」）。这条路径**不写任何日志**。
2. **没有模型端点、没有显式预算时，会不会被打开？** 不会。`model` 三项（endpoint / model / budgetMs）必须同时给出且全部显式（`supplement-plugin.ts` `parseModel`），没有默认值、不读环境变量；resident 今天不传 `model`，生产路径恒为 inert。
3. **补充的意外异常会不会越过局部边界、吃掉原通知？** 不会，两道边界都在：模块内把所有可命名失败翻成 `undefined`；attention 在**投递前**对「取补充 + 组装版面」整段 `try/catch`，catch 只写一行 `模型补充：未预期异常 → 未附加` 并继续用原 `lines`。`note()` 本身吞掉 logger 抛出的异常（`plugin.ts:165-173`），所以连日志写入也不能阻断投递。产品级失败注入 11 条用例覆盖端点 5xx、非 JSON、超时、引用不符、材料缺件、身份不符、弃权。
4. **标签 / 版面的所有权是否唯一？** 是，见 §13.8：常量一处、拼接一处、写入路径一条。

**残留风险（如实报告，本轮不修）**：attention 现在把补充服务列为**第七项硬依赖**（`plugin.ts` 的 `requires`）。若将来某个组合加载了 attention 却没有加载补充插件，attention 会因缺 capability 而不激活——**CI 失败通知会整体静默**，而不是「只有补充缺席」。今天不存在这种组合（两者同在 `chain` 里，resident 一次性加载，测试也断言了七项在齐才 active），但接 CLI 时必须保证「补充满载失败」不会先于「通知仍要发出」发生：参数校验要在加载前完成，失败要落到启动期错误上，而不是让 `chain` 静默少一个成员。
