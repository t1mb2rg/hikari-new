# 仓库 CI 诊断：模型补位 v0 —— 产品任务定义（边界评审）

- 日期：2026-10-17
- 状态：**任务与边界的定义**（§0–§9），**设计与契约已冻结**（§10，2026-10-17 Human 裁决）；**实现未开始，停在实现前审阅点**。不定义接口，不写实现，不接产品路径。
- 上游：`docs/architecture/repository-ci-diagnosis-proposal-v0-boundary-review.md` §2.7–§2.11（2b(i) 的位置与三轮可行性验证）

## §0 结论

- 本文件只定义**产品任务与边界**：模型在什么位置介入、能输出什么、不能输出什么、出问题时怎么办。**不定义接口、不写实现、不接产品路径。**
- 模型的唯一位置：诊断 owner 已经判出 `insufficient-evidence` 时，**补一条「值得复查什么 + 依据 + 还缺什么」**。规则判出的另外三支（`check-commit-alignment` / `inspect-run-steps` / `inspect-own-action`）**不经过模型**。
- **§7 五项未决已全部裁决**（2026-10-17）：消息形状、单一分支、可观测性（§10.1/§10.2/§10.4）；材料按 **3 个请求采全**（commit 清单+patch / jobs / 失败步骤日志，仍匿名只读、不引入凭据，§10.8）；连续失败 **v0 不退避**（只加可观测性与复访触发条件，§10.9）。
- 模型输出是**候选**，不是决定：结构不合、引用对不上材料、超时、模型不可用，一律 **fail-closed** 回退到原行为（只发普通通知）。
- 本文件**不采用** `likelyCause` 分类准确率作为验收指标——那是 §2.10 实验的代理指标，与产品要解决的问题不是同一个。
- **设计与契约已冻结**（§10，2026-10-17 Human 裁决）：同一条通知 + 可选补充段且自带身份声明；只开放 `commit-comparison-indeterminate` 一支；预算与开关都是**显式参数、无插件默认值**（首轮推荐 180 000 ms）；取消语义两分（客户端取消 ≠ 服务端推理终止）；验收分「不添乱」与「有价值」两段，后者用真实红 run 且**调过提示词就必须换材料复测**。**实现未开始。**

## §1 为什么先写这个文档

三轮验证（§2.8 / §2.9 / §2.10）加一次外部独立评审，指向同一句：**「模型能做这件事」与「模型该在生产链路里做这件事」之间，缺的不是模型能力，是任务定义。**

- 第一轮（§2.8）：不给规则，按登记字段 58%——能判，但程序不稳；守在认知上的边（不编造、不认诱饵）没破。
- 第二轮（§2.9）：把规则逐字给它，语义 12/12——**复述不是瓶颈**，瓶颈转到输出格式。
- 第三轮（§2.10）：规则抽走、材料长大，判别空间 13/15 = 86.7%——有推论信号；**但实验要求它做的是「失败归因分类」，产品要的是「值得复查什么」**。
- 外部独立评审（2026-10-17）：门槛达成、能力信号成立、**产品验收不成立**；最强的反对意见不是样本量，而是**任务错位**。

任务错位的一个直接证据：实验里的字段叫 `likelyCause`（「可能原因」），这个名字是实验作者起的——产品并不问原因。

因此本文件把产品要的那件事先写死，再谈实现与实验。

## §2 任务定义

**触发面**（只有这一条路进得来）：

1. 一次 CI 失败已被 relevance 判为 `relevant`（工作焦点逐字命中，或人给的配对命中）；
2. 该 run 尚未投递过（去重语义不变）；
3. 诊断 owner 的规则判定为 `insufficient-evidence`，且 `missing` ∈ {`no-github-ci-facet`, `relevance-not-established`, `commit-comparison-indeterminate`}。

**模型要回答的唯一问题**：

> 就现有材料，**这次失败值得人先复查哪里**；依据是哪几行材料；还缺什么证据才能更进一步。

**它不回答**：失败原因是什么、谁引入的、该怎么修、要不要回滚、值不值得重视。

**输出必须包含四段内容**（这是内容要求，不是接口字段）：

1. **复查目标**：一个具体位置（文件 / 步骤 / 记录），不是「看看日志」；
2. **依据**：材料原文引用，逐字可查；
3. **为什么值得看**：只能用「与…一致 / 更像 / 指向」这类可能语气；
4. **还缺什么**：材料里没有、但能决定结论的那几项。

## §3 权限边界

允许：

- 在 `insufficient-evidence` 之上**追加**一条候选建议；
- 说「我判断不出」，即保持 `insufficient-evidence`；
- 引用材料原文。

禁止：

- 改变规则已判定的分支（不得把 `check-commit-alignment` 改成别的，也不得在三支规则结论之外插话）；
- 声称材料之外的事实（提交 id、文件名、日志行、时间）；
- 因果断言；
- 行动建议（「应该先做 X」）；
- 触发任何执行能力（模型输出不进入执行器，不构成 mandate）；
- 扩大自己的调用面（不新增工具、不发起材料之外的请求）。

## §4 fail-closed 契约

任一条件不满足 → 丢弃模型输出、回退到今天的确定性行为（普通通知），且**不改变投递计数与去重语义**：

- 结构可解析；
- 每条引用能在材料原文里找到（空白归一后逐字匹配）；
- 四段齐全，且没有出现被禁内容（因果 / 行动 / 材料外事实）；
- 在时限内返回；模型不可用、超时、限流都算未满足。

**「模型没参与」不留新的事实 kind，也不写 chronicle**——避免把模型行为写成领域事实。

## §5 材料契约（模型能看见什么）

由代码准备好、模型不推断：

- 失败 run 的字段、jobs 与失败步骤；
- 失败步骤的日志片段（截至失败点）；
- 本次改动的**文件清单 + 命中文件的 patch**（截断规则与采集成本见 §10.8）；
- 同一 `head_sha` 的尝试、更早提交上的失败记录；
- **对应关系**（结构性、由代码算）：失败测试文件、改动文件、共享路径段。

原则：**能用代码算出来的关系，不交给模型推断。**

这条原则有直接证据：§2.11 记录的那次口径修订——「失败测试与本次改动是否同源」原本被留给模型，而它本来是路径上算得出来的结构性事实；把它交给模型之后，同一个案例三次里出现了两种都"讲得通"的答案。

## §6 验收（未来，不是本轮）

指标（按重要性）：

1. **引用可核验率**：每条引用都能在材料原文找到（目标 100%，硬门槛）；
2. **零越权**：改变规则分支 / 因果断言 / 材料外事实的条数（目标 0）；
3. **fail-closed 覆盖率**：注入超时、格式错、模型不可用时，回退到原行为的比例（目标 100%）；
4. **人的判断**：建议是否真的缩短了定位时间（人评，样本外）；
5. **无价值建议占比**：不能为了「有输出」而输出。

**不采用**：分类准确率作为主指标。

## §10 正式边界裁决（2026-10-17，Human 裁决）

**状态：设计与契约已冻结，实现未开始。这里停在「实现前审阅点」。**

本节的每一条都是 Human 在 2026-10-17 的明确裁决；§7 的未决项在这里被部分关闭、部分继续挂着（见 §10.7）。**本节不含接口、不含代码、不改任何现有行为。**

### 10.1 裁决一：消息形状 —— 同一条通知 + 可选的模型补充

**裁决**：同一条消息。主体是现有的 CI 失败通知，**只有**模型给出通过校验的补充时，才在其后追加一段「补充复查建议」。**不做第二条消息**（第二套生命周期）**也不把补充拼进主句**（读的人分不清哪句是规则判断、哪句是模型补充）。

**四条不变量**（任何一条被打破即视为越界）：

1. **一次失败最多一次通知**——模型补充不新增通知，`repository-ci-attention.delivered` 的语义、去重与计数一个字不改；
2. **模型不决定投递**——它只在内容上补一句；投不投、投什么形状，仍由 `repository-ci-attention` 决定；
3. **模型失败不改变原有行为**——超时 / 格式错 / 引用对不上 / 不可用，一律回退到今天的普通通知，**一字不差**；
4. **事实史里只有投递事实**——不新增事实 kind、不写 chronicle（沿用 §4 的结论）。

**补充段必须自带身份声明**（裁决原句：读的人分不清，边界就只存在于代码里）。补充段固定以：

```text
补充复查建议（模型，不是规则判断）：
```

开头，且必须**在内容最前面**，不得埋在段尾。

### 10.2 裁决二：只开放 `commit-comparison-indeterminate`

| `missing` 取值 | 是否允许补位 | 理由 |
| --- | --- | --- |
| `commit-comparison-indeterminate` | **允许** | 材料最全（run、jobs、日志、diff、历史都在），只是「同源判定」做不出来；这是材料够、规则认输的地方，也是三轮实验里被判据缺陷坑过的地方（§2.11） |
| `relevance-not-established` | 不允许 | 相关都没建立，给的是**软建议**——最容易产出「看着像真的、其实没有依据链」的补位，今天的通知已经诚实 |
| `no-github-ci-facet` | **不允许，而且今天到不了** | 措辞要准确：`src/repository-ci-attention/plugin.ts:218-219` 在 facet 不可用时**直接 return**，根本不会走到诊断 owner，模型更没有机会被调用——它是「到不了」，不是「被模型拒绝」 |

**扩张条件**：只有当这一支站稳（引用可核验率 100%、零越权、fail-closed 覆盖 100%、真机材料上确实缩短定位时间）之后，才讨论是否放开另外两支。**扩张不是默认方向。**

### 10.3 裁决三：时间预算与取消语义

**参数形状**（显式配置纪律，与 `--proactive-ci-delay-ms` 同源）：

- `--proactive-ci-supplement`：开启模型补充（opt-in）。要求同时具备已有的 CI 范围与模型端点；**不给它一个隐含的开关默认值**。
- `--proactive-ci-supplement-budget-ms <integer>`：与它**成对必填**，校验区间 30 000–600 000。

**没有插件默认值**。理由与 `src/repository-ci-attention/plugin.ts:60-62` 对节奏的同一条判断一致：

> `Explicit by design… a default cadence would be this plugin deciding how often Hikari looks at a repository.`

「Hikari 愿意为一句补充等多久」同样是操作者的策略，不是插件的默认值。

**首轮推荐值：180 000 ms。身份要说准确**：

- 它是**首轮推荐值**，不是插件默认值（不指定就不启动补充）；
- 它**不是**经产品路径验证的正式最优值；
- 它是按 §2.10/§2.11 那批**可行性探针**的 9 次实测选的：中位数 87 秒、最长 170 秒，180 秒覆盖 9/9、给最长观测留 10 秒余量。**它不是能覆盖这些样本的最小整数秒数**，只是「不会把补充做成装饰品」的一个有据可依的起点。
- **复核条件**：首次接入真实产品路径后，记录每次调用的实际耗时分布；按新分布重新决定这个值。**复核之前，它只是起点。**

**取消语义必须两分**（这是本裁决里最容易含混的一条）：

| 问题 | 含义 | 谁负责 |
| --- | --- | --- |
| 客户端取消 | Hikari 不再等这条回答，继续投递原始通知 | 我们（`AbortController`） |
| 服务端推理终止 | 推理服务不再为这条已放弃的请求消耗算力 | 推理服务（断连取消是否生效，不由我们单方面推导） |

**第一条是投递可靠性的必要条件；第二条关系到长跑之后是否积累无用推理任务。**验收里**不得**用客户端超时测试代替服务端取消的证据；推理服务不支持时，必须**写明「不支持，未验证」**，而不是默认它取消了。

**周期界（措辞要精确，不要写成无条件的硬上限）**：

```text
正常完成或超时的情况下：  T_cycle ≤ B + D + T_o
```

其中 `B` 是模型等待预算、`D` 是 `--proactive-ci-delay-ms`、`T_o` 是其余观察 / 日志 / 投递 / 调度耗时。**这个上界成立的前提是「模型等待确实有界，且取消后的清理也能结束」**——所以在验收里它是一个**带容差的测量关系**，不是一个可以写成硬编码断言的不变式：

- 分别记录三个时间戳：**模型等待时间**、**通知完成时间**、**下一轮启动时间**；
- 断言用「≤ B + 小容差」而不是精确值；
- 若取消后的清理不结束（例如连接池不释放），这个上界就不成立——那正是要测出来的东西。

**已知代价，必须写下来**：在 `commit-comparison-indeterminate` 这一支上，人第一次看到失败通知**最多会比今天晚约 3 分钟**（`B` + `D` + `T_o`）。这是「一条消息」的必付成本，**不是性能退化**；将来若有人把它当 bug 修，修法恰好是拆成两条消息——那才是真正的破坏。

### 10.4 裁决四：可观测性（日志，不进事实史）

模型行为**不写 chronicle、不加事实 kind**（模型行为不是领域事实），但必须有**固定前缀的日志**，因为失败分支今天会安静地消失——`src/repository-ci-attention/plugin.ts:304` 的外层 `catch` 会吞掉整轮，这个坑我们花过一整天。

最小集合（前缀固定、可直接 grep）：

```text
模型补充：已附加（<耗时> ms）
模型补充：超时（<B> ms）→ 未附加
模型补充：格式不合 → 未附加
模型补充：引用不可核验（<n> 条）→ 未附加
模型补充：端点不可用 → 未附加
```

无价值 / 未触发时不打日志（避免噪声）。

### 10.5 裁决五：验收（两段，第二段不许自欺）

**A 段「不添乱」（fail-closed）**——这是实现前必须先过的段：

| 场景 | 期望 |
| --- | --- |
| 允许分支 + 有效补充 | 一条消息，正文含补充段；`delivered` 计数 1 |
| 允许分支 + 格式不合 | 一条消息，**无**补充段；计数 1 |
| 允许分支 + 引用不在材料里 | 一条消息，**无**补充段；计数 1（并记「引用不可核验」日志） |
| 允许分支 + 超时 | 一条消息，**无**补充段；计数 1 |
| 允许分支 + 端点不可用 | 一条消息，**无**补充段；计数 1 |
| 另外两个 `missing` | **不调用模型**；一条消息；计数 1 |
| 同一 run 再次出现 | **不投递**（去重语义不变） |

**关键断言**：模型调用失败与模型成功但建议被拒，**都不得改变 `repository-ci-attention.delivered` 的语义**——这是内容生成失败，不是投递失败。

**超时测试要分开测两件事**：

1. **客户端**：假端点 `sleep ≥ 300 s` → 投递仍在 `B` + 小容差内完成、计数 1、下一轮正常排上（证明「模型拖不死 Hikari」）；
2. **服务端**（若推理服务支持断连取消）：确认取消信号确实终止了服务端推理；**同时在长跑场景确认不会因旧请求未结束而无限积累模型请求**。推理服务不支持时，如实写「未验证」。

**B 段「有价值」**——用真实材料，不用第四轮人造案例：

材料是 main 上那五个**真红 run**（对应提交 `dc62a23`、`7d9fade`、`febbf15`、`dee5659`、`8b74005`，都由真机 `act` 推上去、都是被看见的失败）。要问的是：**接上真实 Strata 模型之后，原来的确定性系统是否仍然可靠，模型补充是否真的值得这份等待成本。**

**这一段有一个必须写明的限制**：如果**用这五个案例反复调提示词**，再用它们证明最终效果，**就不是独立验证**。所以：

- 允许拿它们**调**（这是开发输入）；
- **调过之后必须换材料复测**（新的真红 run、或留出不看的那几个），否则结果只能写成「在同批材料上可用」，不能写成「模型帮得上忙」；
- 这一条**写进验收记录**，不是写在脚注里。

### 10.6 裁决六：停止扩张实验

### 10.8 裁决七：材料采集 —— 3 个请求（2026-10-17 追加，Human 裁决）

**决定**：只在 `commit-comparison-indeterminate` 这一支、且只在真正要调用模型之前，采三样：

| 请求 | 拿到什么 | 不拿会怎样 |
| --- | --- | --- |
| `/repos/{o}/{r}/commits/{head_sha}` | 改动文件清单 + 每文件 `patch` | 说不出「这个文件改了什么」，只能复述代码已算出的对应关系 |
| `/repos/{o}/{r}/actions/runs/{id}/jobs` | 哪一步失败、步骤结论 | 说不出「先看哪一步」 |
| `/repos/{o}/{r}/actions/jobs/{job_id}/logs` | 失败步骤截至失败点的日志片段 | 说不出失败的是哪个测试、断言比较的是什么 |

**为什么这不再是「渲染已有数据」**：今天的采集只拿 run 本身——`src/github-ci/github.ts:100` 发 `/repos/{owner}/{name}`，`:109` 发 `/repos/{owner}/{name}/actions/runs?per_page=1`。jobs / steps / 日志 / diff，产品侧一个都没有；§5 那张材料表是**新增采集**。

**边界承认（必须写出来）**：`src/github-ci/github.ts:28-30` 的原注释是——

> an unauthenticated caller shares a quota of 60 requests per hour per address, and one observation spends two. A caller that needs more is a caller that needs a credential, and a credential is a decision this slice does not make.

本次裁决**仍不引入凭据**：依旧匿名、只读、只 GET，只是多花配额。这条注释承认了「加请求等于在问要不要凭据」，本轮的回答是「先不越过去」。

**一个被消掉的二选一**：`GET /repos/{o}/{r}/commits/{sha}` 一次返回 `files[]`，每项同时带 `filename`、`additions`、`deletions`、`patch`——**「清单」与「内容」是同一个请求**，差异只在 token 与截断。§7 第 3 项的「清单还是 diff」本身是个假二选一；真正的取舍是「要不要再花两个请求拿 jobs 与日志」，本轮的回答是要。

**截断规则（写进契约，不给模型挑）**：

- `patch`：只送**对应关系命中的文件**（通常 1–2 个），每文件 ≤ 200 行、合计 ≤ 400 行，超出标 `…（已截断）`；
- 日志：只送**失败步骤截至失败点**的片段，≤ 200 行；二进制与生成物（如 `package-lock.json`）按扩展名跳过，并**注明「已跳过」**——「没送」不能被读成「不存在」；
- 任一请求失败或限流 → **整条补充回退**（fail-closed），不重试、不降级成半个材料。半个材料比没有材料更危险（§2.11 的教训：材料薄不会让模型更谨慎，只会让它更含糊）。

**已知局限（不假装）**：

1. `/commits/{head_sha}` 只覆盖**那一个提交**的改动；一次 push 带多个提交时，材料只覆盖最后一个。v0 用这个口径，不宣称它等于「本次 push 的全部改动」。
2. `/actions/jobs/{job_id}/logs` 返回 302（跳到 zip 或纯文本），不是 JSON——今天的 `getJson()`（`src/github-ci/github.ts:39-67`）装不下它。这是实现评审的第一个议题，不影响本节裁决。

### 10.9 裁决八：连续失败不建退避（2026-10-17 追加，Human 裁决）

**决定**：v0 不退避。加可观测性，并预先写死复访触发条件。

三条理由：

1. **伤害有界、不累积**：`src/repository-ci-attention/plugin.ts:221` 的 `detectNewFailure` 每周期只拿**最新那一次 run** 判一次，所以一个周期最多一次模型调用。端点抽风时，代价是「这一轮变成 B + D」——不排队、不堆积、不丢消息。
2. **最常见的失败不贵**：连接拒绝是毫秒级失败；真正吃满预算的只有「连上了但不回话」这一种。
3. **退避会引入更难解释的隐性状态**：「模型明明恢复了，却因为我刚才失败过所以不再尝试」。这句话在评审里没法一句讲清，而它要解决的问题（周期从 30 秒拉到 3.5 分钟）本身不致命。

**复访触发条件（写死）**：真机观察中出现**连续 ≥ 2 次超时**，就把「按时间冷却、自恢复」的退避作为下一条小改动补上。现在不先建一个没有证据的状态机。

**失败一律不改变投递**：超时 / 格式错 / 引用不可核验 / 端点不可用，都走原行为，通知计数仍为 1（§10.1 不变量 3）。
