# Hikari 核心架构 v0

> 状态：**冻结 / 可进入实现准备**
>
> 目的：给 Hikari 第一阶段实现提供足够明确、但不过度设计的架构边界。
>
> 本文冻结的是 **v0 必须遵守的结构与不变量**，不是未来所有实现细节。没有真实需求证明必要之前，不继续扩展核心抽象。

---

## 0. 北极星

Hikari 不是一个等待用户调用的聊天程序，也不是一个由单一 Agent Loop 驱动的工具集合。

Hikari 应当：

- 持续存在；
- 保持跨时间、跨模型、跨设备的连续性；
- 感知环境变化并理解其中的重要变化；
- 从共同经历中形成可修订的记忆与成长；
- 在合适的时候主动介入；
- 在获得能力与权限时真实完成事情；
- 对“做过什么、知道什么、不知道什么”保持可验证的诚实。

核心判断：

> **统一的是“我”，分布的是观察、判断与行动。**

> **共享事实，不共享控制。**

---

## 1. v0 总体结构

```text
持续身份
+
事实史
+
局部世界视图 / 记忆 / 目标
+
多个自治插件
+
少数明确的交互机制
+
真实副作用的统一行动边界
```

Hikari 不存在唯一中央大脑。

传统 Agent Loop 可以存在于某个自治插件内部，但不能代表整个 Hikari。

---

## 2. Runtime：薄运行宿主

Runtime 只负责通用运行机制。

### v0 负责

- 插件加载、启动、停止与卸载；
- 插件资源的归属与清理；
- Service 注册、发现与依赖满足；
- Event 注册与派发；
- 插件配置的基础验证；
- 通用取消、任务与生命周期原语。

### Runtime 不负责

- 用户语义；
- Memory、Goal、World 等领域意义；
- Provider 的业务选择策略；
- 行动是否值得执行；
- 人格与最终表达；
- 全局判断；
- 全局状态管理。

原则：

> **Runtime 控制“怎么活”，不决定“为什么活、该做什么”。**

---

## 3. Plugin：唯一的运行扩展单元

v0 不建立 AgentPlugin、VoicePlugin、SensorPlugin、StatePlugin 等业务继承树。

Runtime 只认识一种 Plugin。

插件的不同由它：

- 提供哪些 Service；
- 依赖哪些 Service；
- 发布 / 监听哪些 Event；
- 拥有哪些资源；
- 内部运行什么逻辑；

自然体现。

插件可以是：

- TTS；
- 前台窗口感知；
- 文件系统 Provider；
- 模型 Provider；
- 工程循环；
- 目标循环；
- 记忆整理循环；

但这些只是业务角色，不是 Runtime 类型。

### v0 Manifest 最小职责

Manifest 只描述插件边界，不描述内部实现。

第一版只需要保留：

```text
identity
├─ id
└─ version

runtime relation
├─ requires
└─ provides

configuration
└─ config schema
```

权限、跨节点暴露规则等未来按真实需求增加。

不要求手工在 Manifest 复制全部 Event、Action、Fact 关系；这些关系未来优先通过契约与工具分析得到。

---

## 4. 插件交互：四种语义，各走各的路

Hikari **没有万能通信层、万能消息对象或统一通信信封**。

### 4.1 Service：需要一个能力

含义：

> “我需要你完成一项明确能力，并得到结果。”

Service 承担主要调用与数据流。

例如：

```text
speech.synthesis.synthesize(text) -> audio
foreground.current() -> foreground info
memory.query(...) -> memories
```

同 Runtime 内，Service 可以直接成为普通内存调用。

### 4.2 Event：通知变化

含义：

> “某件值得其他插件知道的事情发生了。”

Event 用于实时通知，不负责普通查询，也不自动成为长期事实。

例如：

```text
foreground.changed
speech.finished
provider.unavailable
```

插件内部实现细节不应升级成公共 Event。

### 4.3 Chronicle：长期事实

含义：

> “这件事真实发生过，未来仍然需要知道。”

事实史保存长期事实与来源，不负责解释事实意味着什么。

### 4.4 Action：改变现实

含义：

> “我要对外部世界产生真实副作用。”

写文件、发消息、执行命令、重启服务、修改外部系统等必须经过统一行动边界。

---

## 5. Service 与 Provider

### 5.1 Service 是语义契约

Service 定义：

- 能力名称；
- 方法；
- 输入；
- 输出；
- 错误语义；
- 契约版本。

它不规定：

- TCP / HTTP / IPC；
- Provider 位于哪个节点；
- 具体实现库；
- 业务选择策略。

### 5.2 Provider 是实现

一个插件可以向 Runtime 注册某个 Service 的 Provider。

消费者依赖 Service 契约，不依赖 Provider 内部实现。

### 5.3 Capability 暂不成为第二套运行机制

v0 中：

> **Service 是 Runtime 的真实原语；Capability 是从公开 Service 形成的能力视图。**

不维护一份与 Service 重复的独立 Capability 真源。

### 5.4 多 Provider 不自动意味着“智能选择”

Runtime 可以知道当前有哪些 Provider，但不能因为方便而发展成全局业务调度器。

v0 仅允许简单、无歧义的 Provider 解析。

复杂选择策略只有在真实领域需求出现后，才由相应领域承担。

---

## 6. 核心共享领域边界

### 6.1 Continuity

回答：

> “这些经历属于谁？”

负责 Hikari 持续身份与生命线连续性。

不负责 Memory、World、Goal、设备认证或权限判断。

### 6.2 Chronicle

回答：

> “真实发生过什么？”

可以成为共享事实基底，但不能成为统一解释中心。

### 6.3 World

回答：

> “在某个范围内，现在是什么情况？”

World 不是一个 `GlobalWorldState`，而是多个有范围、来源、新鲜度和不确定性的局部视图。

### 6.4 Memory

回答：

> “过去的经历让我理解了什么？”

Memory 是可修订解释，不是事实真源。

### 6.5 Goal

回答：

> “什么期望状态需要跨时间持续推进？”

Goal 表示长期承诺，不负责自己查询世界、自己决策下一步或自己执行动作。

### 6.6 Judgement

**不建立中央 Judgement Domain。**

判断是自治插件内部的局部活动。

---

## 7. 局部自治

Hikari 可以同时存在：

```text
对话循环
感知 / Awareness 循环
目标推进循环
工程循环
维护循环
记忆整理循环
```

每个自治过程只读取自己需要的视图和 Service，做局部判断，并产生有限输出。

没有任何自治插件天然拥有“全 Hikari 控制权”。

禁止为了协调方便增加 Super Orchestrator。

---

## 8. 行动与并发正确性

核心原则：

> **意图可以等待，判断不能冻结，动作必须新鲜。**

多个自治过程允许基于旧状态开始思考，但真正改变现实之前必须重新确认相关当前状态。

如果目标已经被其他过程满足：

```text
重新读取状态
↓
发现目标已满足
↓
直接结束
```

如果仍然需要行动，再形成新的动作并执行。

v0 只要求：

- 对真正需要并发保护的资源使用局部状态版本 / 前置条件；
- 行动执行前验证相关状态；
- 正确性不能依赖调度器“刚好排对顺序”。

不设计整个 Hikari 的全局版本号。

---

## 9. v0 实现范围

第一阶段实现以 **单 Runtime、本地进程内插件** 为目标。

必须验证：

1. 插件生命周期成立；
2. `requires / provides` 可以形成稳定 Service 依赖；
3. Service 可以完成有返回值的数据调用；
4. Event 可以完成实时通知；
5. 插件卸载时资源能够正确清理；
6. Provider 消失时依赖关系能够正确收敛；
7. Runtime 不需要理解任何具体业务语义；
8. 不需要万能消息对象或统一通信信封即可工作。

第一阶段可以使用测试插件验证机制，不要求立刻迁移旧 Hikari 功能。

---

## 10. 明确延后，不在 v0 继续设计

以下问题已经知道未来可能需要，但 **当前冻结，不继续展开**：

- 跨 Runtime Service；
- 节点之间的连接协议与传输格式；
- 远程 Event；
- 跨节点事实同步与去重；
- 节点密码学身份与撤销；
- Provider 的复杂智能选择；
- Service 的通用对象 / Subject / Scope 模型；
- 全局 Entity 模型；
- 流式大对象与音视频传输抽象；
- 分布式租约与 fencing；
- 离线信任窗口；
- 完整权限系统；
- 多节点强一致；
- 完整 Skill 体系；
- 最终 Manifest 格式。

触发这些设计的条件必须是：

> **真实实现已经出现无法被当前模型正确表达的问题。**

而不是：

> “未来可能会有，所以现在先设计。”

---

## 11. 明确禁止重新引入的结构

除非重新进行架构审查，否则不得引入：

- 中央 AI Brain；
- 中央 Judgement；
- Super Orchestrator；
- GlobalWorldState；
- GlobalStateManager；
- 万能 Service；
- 万能消息对象；
- 所有交互必经的统一通信层；
- 所有 Provider 的通用智能调度器；
- 按业务类型不断扩张的 Plugin 基类树。

---

## 12. v0 核心不变量

1. **一个 Hikari 不等于一个 Runtime。**
2. **Runtime 负责机制，不理解领域意义。**
3. **Plugin 是唯一运行扩展单元，不按业务类型建立继承树。**
4. **Service 负责有返回值的能力调用和主要数据流。**
5. **Event 只负责值得跨插件通知的实时变化。**
6. **Event 不等于长期事实。**
7. **查询信息与改变现实是不同操作。**
8. **真实副作用必须经过 Action 边界。**
9. **改变现实必须基于当前状态，而不是旧判断。**
10. **Chronicle 共享事实，但不共享控制。**
11. **不存在中央判断器或超级协调器。**
12. **分布式能力要给未来留路，但 v0 不实现未来本身。**

---

## 13. 冻结规则

从本文冻结开始：

- 不再因为纯理论问题继续增加核心抽象；
- 新概念必须由至少一个真实实现问题驱动；
- 如果现有架构无法表达真实需求，先做 Boundary Review，再修改本文；
- 实现完成后必须做 Architecture Review，检查代码是否穿透当前边界。

当前策略：

> **今天的实现足够简单，明天的路没有被堵死。**
