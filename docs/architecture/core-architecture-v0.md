# Hikari 核心生态架构 v0

> 状态：阶段性架构检查点
>
> 目的：汇总当前已经形成的核心架构共识，并明确哪些旧思路已经被推翻、降级或暂缓。
>
> 本文不是最终实现规范。它记录的是当前阶段已经足够稳定、可以继续向下设计的架构方向。

---

## 1. 总体方向

Hikari 不采用“一个中央大脑控制所有行为”的结构。

当前架构更接近一个长期存在的生态系统：

```text
统一连续身份
+
共享长期事实
+
共享认知资源
+
多个局部自治过程
+
按语义选择交互方式
+
通过规则和状态校验协调
```

核心判断：

> 统一的是“我”，分布的是“思考与行动”。

以及：

> 统一的是规则和契约，自治的是插件。

---

## 2. 运行时不是 Hikari 本身

运行时（Runtime）只负责运行机制：

- 插件生命周期；
- 服务注册与发现；
- 实时事件；
- 作用域与隔离；
- 资源所有权与清理；
- 通用任务、调度、存储原语。

运行时不理解：

- 用户；
- 记忆；
- 目标；
- 世界状态；
- 权限语义；
- Hikari 的人格与判断。

一个 Hikari 可以跨多个 Runtime 存在。

例如：

```text
同一个 Hikari
├─ 云端 Runtime
├─ Windows Runtime
├─ 手机 Runtime
└─ 未来其他节点 Runtime
```

节点可以上线、离线、重启，Runtime 实例可以更换，但 Hikari 的连续身份不因此改变。

---

## 3. 核心共享语义

### 3.1 连续性

连续性回答：

> 这些经历属于谁？

它负责 Hikari 身份与生命线连续性，不负责设备认证、权限、记忆、目标或行动。

### 3.2 事实史

事实史回答：

> 真实发生过什么？

事实史可以成为共享事实基底，但不能成为统一解释中心。

它记录事实、来源、顺序与因果，不负责判断事实意味着什么。

### 3.3 世界视图

世界不是唯一的全局状态对象，而是一组有范围、有来源、有新鲜度的当前状态投影。

例如：

- 用户活动视图；
- 设备状态视图；
- 工程状态视图；
- 当前能力视图；
- 日程上下文视图。

不要求所有视图在任何时刻都完全一致。

### 3.4 记忆

记忆表示 Hikari 从长期经历中形成的、可以被修订的理解。

记忆不是事实真源，也不应成为一个知道全部内容的中央对象。

每条记忆应尽量保留来源、时间、置信度、适用范围与修订关系。

### 3.5 目标 / 承诺

目标表示跨时间持续存在的承诺，而不是某一次局部判断。

目标可以跨模型、跨进程、跨 Runtime 持续存在。

“判断”不再作为一个独立中央领域存在。

---

## 4. 局部自治，而不是中央判断

Hikari 可以存在多个长期自治过程，例如：

```text
感知循环
目标循环
对话循环
工程循环
维护循环
记忆整理循环
```

这些过程各自：

```text
被变化 / 任务 / 条件触发
↓
读取自己需要的局部视图
↓
做局部判断
↓
产生事件 / 意图 / 事实候选
↓
结束本次活动
```

不存在必须接管全部思考的“中央判断器”。

判断是一种局部活动或能力，而不是一个全局唯一服务。

传统 Agent Loop 可以作为某个自治插件内部的一种实现方式，但 Hikari 整体不是一个 Agent Loop。

---

## 5. 插件不是单纯的“功能扩展”

插件是由 Runtime 管理、拥有独立生命周期和资源边界的运行单元。

当前可以观察到三种常见角色：

```text
能力型插件
→ 提供文件、Shell、GitHub、模型等能力

自治型插件
→ 感知循环、目标循环、工程循环等长期活动

桥接型插件
→ 在不同语义边界之间转换，例如把行动回执形成长期事实
```

这只是语义分类，不要求在代码层建立三个固定基类。

领域也不等于插件。

领域回答“谁拥有这个意义”，插件回答“哪个运行单元实现这部分能力”。

---

## 6. 通信：放弃统一超级协议

当前正式放弃“所有交互都必须经过统一通信信封 / 万能消息协议”的方向。

原因：

- 会把通信机制本身变成新的中心；
- 会导致插件承担大量与自身语义无关的元数据；
- 会把本地简单调用强行包装成分布式消息；
- 容易出现类型爆炸与万能消息对象。

恢复为少数几种明确交互方式：

```text
需要一个能力
→ 服务调用

告诉别人发生了变化
→ 实时事件

未来必须证明发生过
→ 事实史

需要改变现实
→ 行动管线
```

没有一个代码实体必须叫“Hikari 通信层”。

通信平面只是架构上的统称。

跨节点通信应尽量下沉到这些机制的底层适配中，而不是泄漏到每个插件的业务代码。

原则：

> 本地语义优先，分布式透明下沉。

---

## 7. 多自治过程的协调原则

不追求一个绝对聪明、永远排对顺序的中央调度器。

当前方向是：

> 调度负责效率，执行校验负责正确性。

### 7.1 意图可以等待，动作必须新鲜

一个长期意图可以排队、等待或被其他过程间接满足。

真正改变现实的动作必须基于当前状态重新形成。

### 7.2 执行前重新验证

某个自治过程等待后重新获得执行机会时，必须重新查看相关状态。

如果目标已经由其他过程满足：

```text
重新读取当前状态
↓
发现不再需要行动
↓
直接结束
```

如果仍需要行动，再生成当前动作。

### 7.3 状态版本

需要并发保护的资源可以具有局部状态版本。

动作记录自己依赖的相关版本，执行时验证这些版本是否仍然成立。

不设计“整个 Hikari 的单一全局版本号”。

### 7.4 资源使用代次

未来在真正出现跨节点资源租约时，可以引入单调增长的资源使用代次，用于拒绝已失效的旧持有者。

该机制属于架构预留，v0 不要求立即实现完整分布式租约系统。

---

## 8. 行动边界

查询信息和改变现实不是同一类操作。

读取世界、记忆、代码等，可以通过正常能力契约完成。

任何会产生外部副作用的行为，例如：

- 写文件；
- 删除资源；
- 发消息；
- 执行命令；
- 重启服务；
- 修改外部系统；

都必须进入行动管线。

概念流程：

```text
行动意图
↓
等待 / 获取必要资源
↓
重新读取当前状态
↓
仍有必要？
├─ 否 → 结束
└─ 是
   ↓
形成当前动作
↓
授权
↓
验证前置条件 / 状态版本 / 资源使用权
↓
执行
↓
回执
↓
长期事实
```

行动正确性不能依赖“调度器之前已经排好了顺序”。

---

## 9. 身份与信任

身份与授权不是同一件事。

当前区分：

```text
Hikari 身份
→ 这是哪个 Hikari

节点身份
→ 这是哪台受信任设备

Runtime 实例身份
→ 这是该节点的哪一次运行

插件 / 工作单元身份
→ 本次调用在 Runtime 内由谁发起
```

插件身份在同一 Runtime 内可以由 Runtime 自己保证，不要求每个插件都拥有独立密码学身份。

跨节点时再引入更强的来源与完整性验证。

原则：

> 安全语义现在确定，密码学实现按真实信任边界逐步增加。

---

## 10. 当前明确放弃或降级的旧思路

### 10.1 中央 Judgement

已放弃。

判断改为各自治过程内部的局部活动。

### 10.2 单一全局 World State

已放弃。

改为多个有范围、有来源、有新鲜度的世界视图。

### 10.3 超级协调器

不采用。

协调优先通过状态版本、资源规则、前置条件、授权和局部重试实现。

### 10.4 统一通信信封 / 万能消息协议

已降级并基本放弃作为核心抽象。

本地服务、实时事件、事实史、行动管线保持各自语义。

### 10.5 全系统瞬时强一致

不要求。

允许不同节点和不同视图短时间存在不一致，关键在于真正改变现实之前验证相关当前状态。

### 10.6 第一版即完整多节点分布式部署

不要求。

架构必须允许分布式，但实现可以先从单 Runtime 开始，再逐步扩展到双节点、多节点与离线同步。

---

## 11. 当前六条核心不变量

1. 一个 Hikari 可以跨多个 Runtime 存在。
2. 自治插件通过公开契约协作，不依赖彼此内部实现。
3. 查询信息与改变现实是两类不同操作。
4. 改变现实必须基于当前状态，而不是旧判断。
5. 调度可以不完美，执行正确性不能依赖调度完美。
6. 不允许任何模块因为“方便”而重新长成中央大脑或万能中转站。

补充原则：

> 共享事实，不共享控制。

> 统一身份，局部自治。

> 统一的是规则与契约，分布的是观察、判断与行动。

---

## 12. 当前仍未完成的问题

这些问题已经识别，但不应在没有真实需求和研究的情况下提前做满：

- 多自治过程之间更复杂的资源冲突如何协调；
- 跨节点身份建立、撤销与离线信任窗口；
- 事实跨节点同步与去重；
- 跨节点服务与事件如何透明适配；
- 哪些状态需要版本控制，版本粒度如何确定；
- 资源租约与使用代次何时真正需要；
- 目标长期推进过程中的偏移检测；
- 最终插件清单、Manifest 与机器可读契约格式。

这些问题进入实现前仍遵循：

```text
明确真实问题
↓
研究成熟系统
↓
理解失败模式
↓
只引入解决当前问题所需的最小机制
↓
实现
↓
复盘
```

---

## 13. 当前阶段结论

Hikari 当前不再被理解为：

```text
一个模型
+
一堆工具
+
一个中央 Agent Loop
```

而被理解为：

```text
一个持续身份
+
共享事实和认知资源
+
多个由 Runtime 承载的自治插件
+
少数明确的交互机制
+
受约束的现实行动边界
```

我们追求的不是一个能一次性规划一切的“大脑”，而是一套能够长期存在、局部自治、持续校正、不会因为任何单一节点或单一过程失效而失去整体连续性的系统。
