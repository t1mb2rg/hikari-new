## 0. 结论先行

M2-b 可以在**不改 `hikari-native/memory/store.mjs` 的公开契约、不改 Runtime、不新增持久化**的前提下完成：
存储层继续只保证"记录形状 + 工程字段 + supersedes 目标存在"，工具层新增"词表 / 跨字段 / 链头 / 长度上限"四类校验。
代价是每次修订一次全表扫描（O(n)），以及两条必须在冻结文档里写明的局限（模型无时钟、模型无法回读 memoryId）。

## 1. 逐条对照冻结原则

| # | 原则 | M2-b 怎么守 | 依据 |
|---|---|---|---|
| 1 | Memory 使用 append-only 存储 | 两个工具都只产生**新行**；不提供 update / delete / 覆盖；旧记录不回写 | `store.mjs:510` 是唯一提交点；十字段无 `supersededBy` |
| 2 | Memory 由 Hikari 全局拥有、单一全局 Store | 复用同一个 `MemoryStore` 实例（`index.js:68`），不新建文件、不加缓存层 | `hikari-native/memory/index.js:68` |
| 3 | 工程负责校验 / ID / 时间 / 持久化 / 完整性 | 新增的四类校验全部是**完整性**规则，不含语义判断 | 见 §3 的"承担 / 不承担"表 |
| 4 | 模型负责判断"什么值得记" | 工具不做去重、不做相似检测、不拒绝"看起来重复"的正文 | 对比：`findings.js:451` 的 Finding 层去重是**同一 claim 的状态机规则**，Memory 没有状态机 |
| 5 | 不自动注入 / 不自动提取 / 不自动过期 | 只在模型显式调用时写；不订阅任何事件、不读会话、不设 TTL | §2.6；M2 §5.3（`:205`）的 TTL 判别标准 |
| 6 | 不改变 World 的 Findings 所有权 | 不碰 `findings.js`；`m-` 与 `f-` 两套 id 空间分离并在工具层显式区分 | 缺口 G-10；`findings.js:68` 的 id 正则 |
| 7 | Runtime 不理解业务 | 新工具仍是 plugin 内 `ctx.tools.register` 的普通工具，不引入新 service 类型、不改 lifecycle | `tools.js:11`、M2 §9.3 |
| 8 | 不建立全局状态中心 / 不让 Provider 决定 Consumer | 工具层队列是模块内私有字段；写入不广播事件、不给其他模块订阅口 | §2.1 |

一行总结：**M2-b 没有新增任何"跨模块通道"**。它只是把已有的 `store.append` 包成两个模型可调用的函数，外加一层校验。

## 2. 七个取舍，为什么是 X 不是 Y

### 2.1 词表与跨字段校验放在工具层，不放进 `store.mjs`

- **X**：`source.kind` 词表、`inference` 与 `ref` 的互斥、`validTo >= validFrom`、`occurredAt` 不晚于调用时的墙钟、
  正文与 `ref` 的长度上限、链头判定，全部写在工具层。
- **Y**：在 `validateRecord` 里加这些规则，或给 `append` 加参数。
- **为什么不选 Y**：
  1. `validateRecord` 的语义是"这条记录的形状是否合法"，它必须能验证**历史上已经写下的每一行**（`store.mjs:105-158` 也被恢复流程复用）。
     时间单位、词表这类规则一旦进存储层，旧数据就得整体满足新规则，否则启动即失败——而存储层没有迁移手段（M2 §4.3 `:164`：不迁移，报错停用）。
  2. 词表与"链头"是**产品语义**，将来要变（例如允许新的 `source.kind`）。放在工具层，变化只影响两个工具；
     放在存储层，变化影响所有历史文件。
  3. M2-a 已经结案（`docs/development/m2a-memory-store.md`），改它的校验等于重开一份已交付的契约。
- **代价**：两条防线之间有一条缝——任何绕过工具直接 `store.append` 的代码（例如测试、未来的导入脚本）不受词表约束。
  这是可以接受的：存储层仍会拒掉形状非法的记录，而"绕过工具写 memory"本身就是越权行为，不在 M2-b 的保护范围内。

### 2.2 链头判定用 `all()` 扫描，不新增存储层索引

- **X**：`store.all().some(r => r.supersedes === targetId)`。
- **Y**：在 `store.mjs` 里加 `hasSuccessor(id)` 或维护反向 Map。
- **为什么不选 Y**：M2 架构 §6.3（`:251`）与 §9.1（启动序列第 5 步）确实写了"构建 supersedes 反向索引"，
  所以加索引**不算越界**——但它是 M2-a 的未竟项，不是 M2-b 的需求。M2-b 需要的能力只是"这条有没有后继"，
  `all()` 一次扫描就能答，且 `all()` 已是公开方法（`store.mjs:259-261`）。
- **代价与升级路径**：每次修订 O(n)，`all()` 还会返回全表快照（`snapshotOf`，`:197-199`）——数百到数千条都还好
  （M2 §4.2 `:156` 的规模判断）。等到 M2-c 真的需要"从一条记忆反查整条修订史"再在存储层加索引，那时是**新增**公开方法，
  要单独走一次 A/B 级流程，不塞进 M2-b。
- **另一条不选 Y 的理由**：工具层算出来的"链头"是随时可以重算的派生结论；把它放进存储层就等于让它变成需要维护的状态，
  而状态一旦持久化就要处理"索引与 jsonl 不一致"——M2-a 已经为 meta 的一致性付过一次代价（`store.mjs:426-438`）。

### 2.3 修订写新行，不改旧行

- **X**：`revise_memory` 调 `store.append({ text, …, supersedes: targetId })`。
- **Y**：`store.update(id, patch)`。
- **为什么**：append-only 是任务第 2 条的冻结前提；M2 §6.3（`:251`）已经解释过为什么不写 `supersededBy`
  （"append-only 流里改旧行会破坏追加语义"），并明确"历史在 Memory 里是一等公民"（`:253`）。
  `update` 还要回答"旧版本去哪"——正是 `supersedes` 已经在回答的问题。所以 `update` 不是更简洁，是**多余的第二套机制**。

### 2.4 修订不继承旧来源

- **X**：新记录 `source` 由模型给；不给落 `{kind:'unknown', ref:null}`。
- **Y**：缺省时复制旧记录的 `source`（"继承"）。
- **为什么不选 Y**：
  1. `source` 的含义是"这一条的依据"（§6.1 `:222`）。修订改了正文，正文的新依据只能由模型判断。
  2. 自动继承等于工程替模型断言"这一版仍依据原来那条证据"——正是 §5.2（`:194`）禁止的那类自动动作。
  3. 信息不会丢：旧指针仍在旧行上，沿 `supersedes` 一步可回溯。
- **代价**：模型每次修订都要重新想"依据变了吗"。这是它本来就该做的判断，不是工程的负担。

### 2.5 一次只修订一条

- **X**：`revise_memory` 的 `memoryId` 是单值字符串。
- **Y**：`memoryIds: string[]`，一次替代多条。
- **为什么不选 Y**：`supersedes` 是单值（`store.mjs:148-152`），批量要写多行，而每行都是独立提交点（`:510`）；
  中途失败会留下"部分修订"这种调用方无法表达也无法撤回的状态。另外批量会让"全部必须是链头"的判定变成集合判定，
  错误信息要指明是哪条，复杂度翻倍而收益只是省两次调用。

### 2.6 工具层抛 `Error`，不返回 `{ ok: false }`

- **X**：校验失败 `throw new Error(<可操作的一句话>)`，与 World 的工具一致（`findings.js:290`、`:465`）。
- **Y**：返回 `{ ok:false, code:'…' }`，让模型自己判断。
- **为什么不选 Y**：工具契约一旦允许"成功也可能带着 ok:false"，模型就必须每次读返回值判断成败，
  多一次分支、多一类误读（把失败当成功的成功路径）。抛错由 runtime 归到工具失败，语义单一。
  存储层的 `MemoryStoreError { code, … }`（`store.mjs:161-168`）仍然保留——它面向**调用方代码**，
  工具层负责把它翻译成一句人/模型都能照着改的话（例如 `SUPERSEDES_UNKNOWN` → "没有这条记忆；`f-` 开头的是 World 的判断"）。
- **代价**：错误码不再出现在工具返回里，测试只能断言消息文本。缓解方式写在任务书：消息开头固定为错误码
  （`MEMORY_SUPERSEDES_UNKNOWN: …`），既给人读也给测试认。

### 2.7 正文超限报错，不截断

- **X**：`text` 超过 4000 字符直接 `MEMORY_TEXT_TOO_LONG`。
- **Y**：截断后保存，返回 `chars` 让模型知道被截了。
- **为什么**：记忆正文的可信度建立在"存进去的就是写下的"。截断是工程悄悄改写模型的事实陈述，
  而且截断点通常落在句中断章取义。
- **4000 这个数字的依据是产品，不是存储**，两件事必须分开说：
  - **输入与上下文规模**：一次写入能带多少内容、工具入参该有多大。这是 4000 的全部理由。
  - **存储完整性**：单行 `appendFile` 的原子性假设是"单行 ≤ 数 KB"（M2 §4.3 `:162`，标 `[H]`，**未实测**）。
    4000 个中文字符最坏约 12 KB，加 JSON 与元数据更大，所以它**不能**被当作原子性的证明；只能说"尽量落在数 KB 量级"。
    真正的完整性保障来自 M2-a 的恢复机制（尾部残片跳过、中间坏行报错、meta 从 jsonl 重建）与将来对 NTFS/POSIX 的实测。
  - 结论：改数值需要产品理由；**给原子性背书需要实测数据**，两者不互相顶替。

## 3. 工程承担什么、明确不承担什么

| 工程承担（工具层） | 工程**不**承担 |
|---|---|
| 拒掉空正文、超长正文、超长 `ref` | 判断这条记忆"值不值得记" |
| `source.kind` 词表与 `ref` 形状 | 判断 `source` 指向的目标现在还在不在（§6.2：不可达是合法状态） |
| `validTo >= validFrom`、`occurredAt` 不晚于调用时的墙钟 | 把"昨天"换算成绝对时间（模型没有时钟，见 §5） |
| 目标存在、目标是记忆（`m-`）、目标没有后继 | 判断修订后的内容"是不是比原来对" |
| 单进程内"判链头 + 写入"串行 | 跨进程共写的锁 |
| 生成 id / `recordedAt` / `seq` | 给 `validHint` 定 TTL、给记忆排优先级 |

第三行值得多一句：`occurredAt` 与 `recordedAt` 的关系看起来像**次序一致性**，其实是**输入合理性检查**——工具层比的是
调用时刻的墙钟，而磁盘上的 `recordedAt` 由存储层的 `#now()` 盖章（可注入：`store.mjs:224`、`:486`），两者不保证相等。
所以本片**不**把它写成记录上的不变量（评审指出过这一点）；这条检查用于**拒绝晚于工具调用时刻的时间戳**。它不能可靠识别
秒与毫秒的混淆：「秒当毫秒」得到的是 1970 年（极早），本检查发现不了；单位正确性主要依赖工具描述约束。未来时间可能意味着
单位错误，也可能意味着模型记录了尚未发生的事件。

而 seq 作为全局序号能直接回答"我这条是不是最新的"。建议在 M2-c 的文档修订里一并改掉，不在 M2-b 里动已冻结文本。

## 5. "不改 M2-a 公开契约"的成立条件

M2-b 只使用存储层已有的五个公开成员：

| 成员 | 用途 | 位置 |
|---|---|---|
| `store.append(input)` | 写入 / 修订 | `store.mjs:458-466` |
| `store.get(memoryId)` | 存在性检查 | `:263` |
| `store.all()` | 链头扫描 | `:259-261` |
| `store.size` | 不需要，但可作就绪断言 | `:231` |
| `store.lastSeq` | 不需要（`seq` 由返回值给出） | `:235` |

成立条件（任一条被打破就要重开架构审阅）：

1. **不新增 `store.mjs` 的导出**（不加 `has()`、不加索引、不加参数）。
2. **不改 `append` 的白名单**（`store.mjs:475-480`）。若将来要允许模型写 `supersedes` 之外的工程字段，说明边界已变。
3. **不改 `MEMORY_FIELDS`**（十字段）。加字段等于改 M2 的记录格式与所有历史行。
4. **不在 plugin 里新建第二份持久化**（缓存、索引文件、sqlite）。派生状态只能留在内存。
5. **不改 Runtime**：不新增 service 类型、不注册事件、不要求 Runtime 理解"记忆"。

## 6. 模块内如何落（不涉及架构，但要先说清，免得实现时发散）

- 新工具放进 `hikari-native/memory/`，与 `tools.js` 并列（读工具）与新增的写工具模块分开：
  读工具依赖 `hikariWorldFindings` service，写工具依赖 `MemoryStore`——两套依赖，塞进一个函数会逼着 `index.js` 传两个参数。
- `MEMORY_TOOL_NAMES`（`tools.js:11`）目前同时被"冲突检查"（`index.js:57-64`）和"ready 行"（`:89-94`）使用。
  扩成四个名字时，这两个地方要一起改——ready 行是订阅方判断"插件到底装上了没"的依据，漏改会让观测与实际不符。
- 工具层队列（防分叉）是写工具模块的私有字段，不是全局单例。

## 7. 风险与未解决

1. **模型没有时钟**（functional §9 第 1 条）：`occurredAt` 大量为 `null` 是可预期结果。**需要人裁决**是否在返回值里带当前时间。
2. **模型无法回读自己写的记忆**（functional §9 第 2 条）：`search_memory` / `read_memory` 只查 World findings。
   M2-b 不做检索扩展，所以修订能力实际只在同一上下文内可用。这是 M2-c 的前置，必须在冻结文档里写明，不能算 M2-b 的缺陷。
3. **无幂等键**（缺口 G-6）：重试会产生两条相似记录。不加的理由见下；风险由"模型自己看得见返回值"承担。
4. **跨进程无锁**（`m2a-memory-store.md` 风险清单第 1 条）：工具层队列只覆盖单进程。

关于第 3 条的取舍：加幂等键需要模型提供一个稳定的 key，但它没有稳定来源（没有时钟、没有 session 序号可用）；
让工程用"正文哈希"当 key 又等于做去重（语义判断）。所以不加，并在冻结文档里写明"重试会写两条"。
