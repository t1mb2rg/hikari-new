# Hikari 开发工具候选记录

> 状态：候选工具清单 / 尚未正式集成
>
> 目的：记录目前发现的、可能用于 Hikari 开发辅助和未来工程能力的外部工具。当前阶段只做记录，不进行正式接入，不因此改变现有架构设计。

---

## 1. 当前原则

Hikari 尚未进入正式实现阶段，因此暂时不围绕具体工具设计核心架构。

这些工具当前仅作为：

- 开发辅助候选；
- 后续 Research Before Build 的研究对象；
- 未来 Engineering / Forge 代码理解能力的潜在 Provider；
- 架构复盘和代码影响分析的辅助来源。

进入正式开发前，应根据当时的代码规模、语言、仓库结构和实际需求重新评估。

---

## 2. GitNexus

定位：仓库级代码知识图谱、调用关系分析、影响范围分析、Agent / MCP 代码理解工具。

当前认为可能适合：

- 开发前查看现有代码结构；
- 修改前做影响范围分析；
- 修改后分析实际影响；
- 辅助 Engineering 理解 Hikari 代码；
- 未来作为代码智能能力的一个 Provider。

当前状态：重点候选，暂不集成。

---

## 3. CodeGraphContext

定位：代码知识图谱与 Agent 代码上下文工具，和 GitNexus 属于非常接近的一类方案。

当前认为可能适合：

- 符号、调用、依赖关系查询；
- 仓库级代码理解；
- MCP 接入；
- 作为 GitNexus 的对照候选。

当前状态：候选，后续与 GitNexus 并排评估。

---

## 4. code-graph-mcp

定位：基于 AST / 调用图的代码关系、影响分析与 MCP 工具。

当前认为可能适合：

- 调用链分析；
- 模块依赖分析；
- 修改影响范围分析；
- 轻量代码图能力参考。

当前状态：候选。

---

## 5. Serena

定位：面向 Coding Agent 的符号级代码理解与编辑工具，更接近 Agent 的“语义 IDE”。

当前认为可能适合：

- 精确查找符号和引用；
- 语义级代码修改；
- 重构；
- 未来 Engineering 的局部精确编辑能力。

和 GitNexus 的初步区别：

```text
GitNexus 类
→ 更偏全局代码结构和影响范围

Serena 类
→ 更偏局部、精确的语义级编辑
```

当前状态：重点候选，暂不集成。

---

## 6. Aider Repo Map

定位：将整个代码仓库压缩成适合模型消费的轻量仓库地图。

当前认为可能适合：

- 低成本提供全局代码上下文；
- 减少模型直接加载大量源码；
- 为未来 Engineering 的上下文管理提供参考。

当前状态：机制参考候选。

---

## 7. SCIP

定位：语言无关的代码智能索引协议 / 数据格式。

当前认为可能适合：

- 研究代码智能底层数据模型；
- 为未来自定义 Code Intelligence Capability 提供标准层参考；
- 避免过早绑定某一个具体代码图谱产品。

当前状态：标准 / 协议研究候选。

---

## 8. Archify

定位：架构描述、架构图、工作流、数据流和架构差异验证工具。

它与 GitNexus 不属于同一层：

```text
Archify
→ 我们认为系统应该长什么样

GitNexus / CodeGraphContext
→ 代码实际上已经长成什么样
```

当前认为可能适合：

- 保存预期架构；
- 架构图结构化表达；
- 开发后的架构复盘；
- 与实际代码依赖图进行对照。

当前状态：重点架构工具候选。

---

## 9. 当前最值得保留的组合思路

后续正式开发时，可以重点评估这种分工：

```text
Archify
→ 架构意图 / 预期依赖

GitNexus / CodeGraphContext
→ 实际代码图 / 影响范围

Serena
→ 精确语义编辑

Aider Repo Map 类机制
→ 低成本全局上下文
```

这不是当前的技术选型，只是一组后续值得验证的组合方向。

---

## 10. 未来评估原则

正式接入任何工具前，至少重新检查：

1. 是否真的解决当前阶段的问题；
2. 是否会侵入 Hikari Core Domain；
3. 是否可以作为 Provider，而不是被核心逻辑写死；
4. 是否支持当前主要开发语言；
5. 是否方便自动化工程工具调用；
6. 是否能和架构评审流程结合；
7. 性能、索引成本和上下文收益是否合理；
8. 许可证是否符合当时的使用场景；
9. 是否有更轻量或更成熟的替代方案。

原则：

> 先记工具，后做选择；先验证问题，再决定集成。
