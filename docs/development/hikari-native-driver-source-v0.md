# Hikari Native v0 — 驱动源：从窗口切换到项目状态变化

> 状态：已生效（`hikari-native/cordis.patch.yml` 第 92-100 行）
> 实现：`hikari-native/project-watch/index.js`（147 行）
> 记录来源：v1 的十六次真实唤醒读数；实现后的第一次真实唤醒（2026-10-30 16:42）——
> 该次唤醒早于 trace 被加入（trace 在 `e3b7393` 才写入代码），因此**没有 trace 记录**，
> 只能从 session 的 turn 14 文本与那次运行的进程时间线确认。

这份文档只回答一件事：**她为什么醒来，以及这个「醒来」到底知道多少。**
它不描述 Project Watch 的实现细节（那是源码的事），而是写下它的边界——尤其是它**不知道**什么。

---

## 一、为什么改

v1 的驱动源是前台窗口标题：窗口切换 → World 发 `hikari/attention/worth` → Activation 唤醒她。

十六次真实唤醒的读数说得很直白：**十四次的窗口只是切回同一个 DSH 标签页**。窗口标题这一类事件几乎不携带「这个项目有没有推进」的信息——它是「用户刚才在看什么」的旁证，不是「事情在发生」的证据。

更根本的理由是口径问题。她声称在意的只有一件事：这个仓库现在到底在做什么、走到哪一步了、有没有卡住。窗口标题与这件事之间隔着一整个语义断层，而 git 状态与这件事之间只隔着一个「变化」的判定。

所以这一版不问「前台是哪个窗口」，改问「这个仓库真的变了没有」。

同一个事件、同一个 Activation、同一个 agent loop——**只有驱动源换了**。这是刻意的：如果换驱动源需要改三个地方，那说明这三个地方耦合错了。

---

## 二、当前驱动源

`project-watch` 每 30 秒做一次只读采样（`index.js:48-65`），并行跑三条 git 命令：

| 采样项 | 命令 | 用途 |
| --- | --- | --- |
| HEAD | `git log -1 --format=%h%x00%s` | 短哈希 + 提交标题 |
| 分支 | `git rev-parse --abbrev-ref HEAD` | 当前分支名 |
| 工作区 | `git status --porcelain` | 脏文件总数与分类计数 |

任何一个子命令失败，整次采样返回 `undefined`，这一轮跳过——**宁可漏报，不误报**（`index.js:47`）。

采样结果与上一条基线比较，变了就发 `hikari/attention/worth`，`reason: 'project-changed'`，载荷里带 `previous` / `current` / `changed`（`index.js:126-133`）。

参数：采样间隔 `30_000ms`，冷却 `120_000ms`（`index.js:24-25`），均由 `cordis.patch.yml` 显式给出。启动时立即采一次基线，不等满一个间隔（`index.js:144`）。

## 三、什么算变化

只比较三项（`index.js:68-75`）：

1. **HEAD 短哈希变了** → 有新提交，或回退了
2. **分支名变了** → 切了分支
3. **工作区脏文件总数变了** → 有文件被修改、新增、删除、暂存或取消暂存

三者都没有变 → 记一条 `quiet`，不唤醒。

有变化但仍在冷却期内 → 记一条 `cooldown`，**不唤醒**（`index.js:113-116`）。

---

## 四、什么不算变化

这一节比上一节重要。

**同样数量的脏文件发生替换，目前识别不了。** 脏文件数从 10 变成 10，但换的是哪十个文件——`diffProject` 只比较 `total`，不看集合（`index.js:73`）。一次「改完 A 文件、顺手开始改 B 文件」在计数上完全静默。

**文件内容变了但计数没变，也识别不了。** 已暂存的文件继续修改、已在脏集合里换了一行——计数不变。

**提交内容变了但哈希没变** 不可能发生；但**提交内容不值得在意**它看不出来——它没有语义。

**未跟踪目录内的变化只算一次。** `git status --porcelain` 对未跟踪目录折叠成一行，目录里新增十个文件，计数仍是 1。

**冷却期内的变化会被吞掉，而且不会补发。** 基线在每次采样后立即推进（`index.js:106`），所以冷却结束后比较的是「最后一次采样」，不是「冷却开始时的快照」。冷却期内发生的 A → B，如果在冷却结束后已经是 B → C，那次 A → B 永远消失。这是 120 秒窗口的代价，写在这里是为了让它变成**已知**，而不是让以后的人把它当成 bug 重新发现一遍。

## 五、三层必须分开

这是这份文档存在的核心理由。

```
状态变化  ≠  内容理解  ≠  重要性判断
   ↑            ↑              ↑
project-watch  World/模型    模型
```

**第一层：状态变化。** Project Watch 只回答「三个指标里有没有一个和上次不一样」。它不知道变化了什么，不知道变了多少行，不知道这次提交是修复还是重构。它的阈值只有防抖与去重，**没有任何「值不值得」的规则**（`index.js:13-15`）。

**第二层：内容理解。** 变化意味着什么，要靠读——读 diff、读提交信息、读文件内容。这一步由她和她的工具完成，不是 Project Watch。

**第三层：重要性判断。** 这次变化值不值得在意、值不值得继续看、值不值得记住，只有模型能判。Project Watch 不参与，Activation 不参与。

**不能让她误以为 Project Watch 理解了整个工作区。** 它观察的是几个有限的状态指标，不是工作区。状态变化不等于内容理解，内容理解不等于重要性判断——任何一层被跳过的结论，都是编的。

---

## 六、这份实现明确不做的事

- **不做内容 diff。** 不看改了什么，只看「有没有改」。
- **不做重要性判断。** 不发「这个重要」的结论，只发「这个变了」。
- **不保证不丢事件。** 冷却期内的变化被丢弃（见第四节）；这是刻意的防抖，不是队列。
- **不跨进程保留状态。** 基线在内存里，进程重启即重建，重启本身不算变化（`index.js:97-102`）。
- **不做多仓库。** 一个实例一个 root。

事件在 turn 运行中到达时的投递语义，是另一件事，单独记录在 `docs/development/hikari-native-event-delivery-v0.md`。
