# M2 设计选项比较

依据：`experiments/m2-code-facts.md`（代码事实）与 M2 任务书的硬约束。
每条候选都写「成立条件 / 成本 / 排除理由」，最后给推荐组合。

约束复述（来自任务书，不重新论证）：不用固定 TTL 表达有效期；记什么由模型判断；不引入向量数据库；每份状态只能有一个所有者；不做 Finding → Memory 自动同步；不建新数据库。

---

## 一、数据模型

### 候选 A：沿用 Finding 结构，只加字段

在 `findings.js` 的八字段上加 `observedAt` / `validFrom` / `validTo`。

- **成立条件**：长期记忆与「当前认为什么是真的」是同一类东西。
- **成本**：最低。投影、检索、工具全部复用，只改 `applyFindingRecord` 与 schema。
- **排除理由**：任务书已冻结三分——Observation（发生了什么）/ Finding（现在认为什么）/ Memory（哪些经历值得未来重用）。三者的**生命周期不同**：Finding 会被推翻、会进终态；Memory 不需要终态，它只需要「越来越旧」。把两者塞进一个结构，等于让「一条被 refuted 的 finding」和「一段值得记住的经历」共享同一套状态机，最后必然要给 Memory 引入它不需要的 `refuted` 语义，或者给 Finding 引入它不需要的「年龄」。**这条排除是边界问题，不是成本问题。**

### 候选 B：完全独立的 Memory 记录，与 Finding 无关

新建 `memoryId` + 自有字段，不引用 Finding。

- **成立条件**：记忆完全自足，不需要回答「这条是从哪条判断来的」。
- **成本**：中。要新建投影、新工具、新检索。
- **排除理由**：丢失来源追溯。她写过 f-003「watch 的 emit 时序」、f-004「唤醒文字与 trace 对不上」，这些判断沉淀成教训时，**最有用的一句话是「这条教训来自哪次验证」**。不引用 Finding 就答不了，只能靠自由文本写一遍，那是复制而不是引用。

### 候选 C：分层，Memory 引用 Finding 但不拥有它

Memory 记录有自己的 id 与生命周期，`source` 里放**指针**（finding id / session seq / file path），指向的证据仍归 World 或 Session 所有。

- **成立条件**：接受「引用而非复制」——读一条 Memory 时，若要知道原始证据，得回去查。
- **成本**：中。多一层间接，检索时要能解析指针（解析失败要能降级成「原始证据不可达」而不是报错）。
- **推荐**。理由：满足任务书「两套数据所有权独立」，同时保留追溯能力；指针失效是可表达的状态（见第三节 `validTo` 的 null 语义），不是异常。

**推荐 C。** 最小字段集（设计推论，待实现验证）：

```js
{
  memoryId,        // 自有命名空间，与 f-* 区分
  text,            // 模型自己写的正文，不设模板
  occurredAt,      // 这件事发生的时间（模型填；未知就 null）
  recordedAt,      // 写下来的时间（工程填）
  source,          // { kind: 'finding'|'session'|'file'|'conversation'|'inference', ref }
  supersedes,      // 可选：这条替代了哪条（修正链）
  validHint,       // 可选：模型自报的「大概多久可能失效」，自然语言
}
```

刻意**不**设的字段及原因：`confidence`（数值置信度会让模型以为工程在替它算概率）；`kind` 分类枚举（一旦有枚举，模型就会先分类再写，而不是先想清楚）；`tags`（容易退化成关键词堆，且检索已经在用词元重叠，再加一层只会互相打架）。

## 二、持久化

### 候选 A：继续用 Session 日志（projection）

沿用 `ctx.sessionProjections.register`，把 Memory 也做成一个投影。

- **成立条件**：长期记忆只在一个 session 的生命周期内有效。
- **成本**：零新增基础设施。
- **排除理由**：投影是 **per-session** 的（`currentFindings()` 用 `ctx.sessions.get(sessionId)` 取当前 session，`findings.js:387-393`）。长期记忆的定义就是「跨 session 还在」。要跨 session，就得重放所有历史 session 日志——成本随对话量线性增长，且 session 归档之后记忆就断了。**这条排除的依据是「投影的作用域是 session」，不是「日志不能用」。**

### 候选 B：独立 append-only 文件

`<hikari 数据目录>/memory.jsonl`，一行一条记录，启动时全量 fold 成内存状态。

- **成立条件**：接受文件级生命周期（创建、追加、损坏恢复）。
- **成本**：中。要处理：追加的原子性（单行 write 是否够）、部分写入的恢复、schema 版本。
- **与现状同构**：这与 Session 投影是**同一个模式**——append-only 事件流 + fold 成状态（`findings.js:379-385` 已经是这个形状）。区别只是作用域从 session 扩到全局。
- **推荐**。理由：满足跨 session，不引入数据库，恢复逻辑与现有 projection 同构（可复用 `apply` 的写法），且纯文本可直接 grep——调试成本低。

### 候选 C：复用 DSH 已有的会话/档案存储

- **成立条件**：DSH 提供一个可写的、跨 session 的存储槽。
- **成本**：未知，需查 DSH 是否暴露这类 service。
- **排除理由（暂定）**：目前没有证据表明 DSH 暴露了这类可写存储；`sessionProjections` 是只读派生，`dsh-tools` / `dsh-session` 都不是通用 KV。**这条留作待核对**：若 DSH 真提供了，B 应当让位给它（少一个自己维护的文件）。见本文末「待核对」。

**推荐 B（附带：若 DSH 提供通用存储则改为 C）。**

## 三、时间与有效性（本阶段重点）

先把分工说清楚，再列候选。

**工程能给什么**：`recordedAt`（写入时刻，可信）；当前时间（读的时候能算 age）；记录的存储顺序。
**工程不能给什么**：这件事实际发生在什么时候（只有模型知道，或只有原始证据里有）；这条记忆现在是否还成立（只有模型能判断语义）。
**因此**：工程负责**提供时间信息与状态表达**，模型负责**语义判断**。这是任务书那句话的直接推论。

### 候选 A：单一 `recordedAt`（现状）

- **成立条件**：所有记忆都是「刚发生的事」。
- **成本**：零。
- **排除理由**：事实表第一条缺口。`recordedAt` 是「我今天想起来记下来」，不是「这发生在昨天」。用它当时间轴，所有记忆的年龄都被系统性地低估——越是重要、越是隔了几天才写下来的经历，就越容易被当成「新的」。

### 候选 B：bi-temporal —— `occurredAt` + `recordedAt`

两个时间都存，读的时候都能看到。

- **成立条件**：模型能区分这两者，并在写的时候填 `occurredAt`。
- **成本**：低。多一个字段，多一段渲染。
- **评价**：必要但不充分。它解决了「时间轴错位」，没有解决「这条现在还成不成立」。

### 候选 C：bi-temporal + 有效区间

在 B 之上加 `validFrom` / `validTo`。

- **成立条件**：模型能给出「这条从什么时候开始成立、到什么时候为止」。
- **风险**：`validTo` 一旦变成必填，就等于把 TTL 换了个名字。
- **关键设计点**：**`validTo = null` 必须表示「未知」，而不是「永久有效」**。这一点如果不在文档与渲染里写死，模型会把 null 读成「永远成立」，而它实际的意思是「我不知道它会什么时候失效」。同理 `validFrom = null` 表示「不知道从哪开始」。

### 候选 D：bi-temporal + 模型自报的失效提示（自然语言）

在 C 之上，允许模型写一句 `validHint`，例如「这个结论大概一周内有效」或「除非 CI 配置改了，否则一直成立」。

- **成立条件**：模型愿意写，且下游不把它当机器可读的规则。
- **成本**：低（一个自由文本字段）。
- **为什么不是 TTL**：TTL 是**工程在时间到达时自动改变状态**；`validHint` 是**模型写给未来自己的判断依据**，工程从不据此自动做任何事——不自动过期、不自动降级、不自动隐藏。到期的动作永远由模型在读到它时自己做。
- **风险**：模型可能写废话（「不确定」）。这不要紧，`null` 和「不确定」本来就是合法答案。

**推荐 D。** 三件事分开：`occurredAt`（事实发生时间）/ `recordedAt`（记忆形成时间）/ `validHint`（模型对未来的预判，纯自然语言）。`validFrom`/`validTo` 作为可选精化，默认 `null`，语义统一为「未知，不是永久」。

## 四、检索接口

事实表第六条缺口：现有 `searchFindings` 只有 `query / limit / offset`（`findings.js:233`），不能按状态或时间筛。

### 候选 A：不动检索接口

- **排除理由**：模型想问「上个月那些还没被推翻的判断」时，没有表达方式。

### 候选 B：加过滤参数（`status` / 时间范围）

- **成立条件**：模型知道自己在按什么筛。
- **风险**：参数一多，检索变成 SQL，模型容易拼错，也容易把「筛选」当成「判断」。
- **评价**：可用但笨重。

### 候选 C：让检索结果自带时间信息，筛选交给模型

返回里带上 `occurredAt` / `recordedAt` / age，模型自己看、自己挑。

- **成本**：最低（只是多渲染几个字段）。
- **风险**：候选集可能太大，模型看不完。
- **评价**：与「工程不替模型做语义判断」一致，但对「时间范围」这种确定性需求不够。

**推荐 C 为主、B 为辅**：默认检索结果自带时间信息；只加一个**时间范围**过滤（`since` / `until`），因为它是确定性的、不需要语义判断的；**不加** `status` 过滤——「哪些还成立」是语义判断，应由模型读结果后自己判，而不是让检索层用 `status` 字段替它筛。

## 五、推荐组合与它好在哪

| 线 | 推荐 | 一句话理由 |
|---|---|---|
| 数据模型 | C 分层 + 引用 | 所有权独立，来源可追溯（候选 A/B 各丢一半） |
| 持久化 | B 独立 append-only 文件 | 跨 session，与现有 projection 同构，不引入数据库 |
| 时间 | D（bi-temporal + 自然语言失效提示） | 时间轴不错位，且不把 TTL 换名 |
| 检索 | C 为主 + 时间范围过滤 | 判断留给模型，确定性筛选留给工程 |

**相对被排除方案的整体优势**：每份状态只有一个所有者（Memory 拥有自己的记录，Finding 归 World）；记忆与对话解耦（跨 session）；所有「多久失效」的判断留在模型侧（工程不做自动过期）。

**这套组合的代价**：多一个需要维护的文件（原子性、损坏恢复、schema 版本）；`source` 指针可能失效，需要「不可达」这个合法状态。
