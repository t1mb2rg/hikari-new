# 三组对照：八行通知 / 零模型机械摘要 / 真实模型补充

日期 2026-10-19。样本在任何模型调用之前冻结（`samples.json`，`frozenAt` 早于 `results.json` 的首次调用）。产品侧提示词、schema、`MAX_CITED` 均未修改，`supplement.ts` 在实验前后都是 `146e53bf9feeafa1bfed9dd7b199b55b82c12fe7`（`results.json` 的 `supplementCommit` 与 `expectedCommit` 相等）。

## §0 结论

1. **在这 5 个样本上，零模型机械摘要 5/5 给出了可核实的失败位置（job / step / 改动文件至少两项正确）；八行通知 0/5 给出任何定位信息；模型补充 1/5 附加。** 这是本批最直接的对比读数。

2. **唯一附加的那一次（run `36327884462`），模型没有指向失败位置，而是建议补看三个背景项**：`Post Setup Node`、日志里的 `skipped 92`、`Node.js 20 is deprecated`。该 run 的真实失败位置是 `test / Build and test`，改动文件 `test/proactive-ci-smoke.test.mjs`。机械摘要在同一个 run 上三行全对。

3. **模型侧 4/5 没有产出**：2 次打满 180 000 ms 超时、1 次 168 379 ms 后端点不可用、1 次引用不可核验。因此「模型定位不如机械摘要」这句话**只有 n=1 的直接证据**，不能说成普遍结论；能说的是**首次附加率 1/5**，以及**附加的那一次没有产生定位增量**。

4. **对「模型补充的实际增量价值」这个问题的回答，本批给出的方向是负面的**：在 180 000 ms 预算与当前提示词下，这段补充在这批样本上既不稳定产出（1/5），产出时也没有超过一条三行的确定性规则。但这个判断的适用范围很窄，见 §7。

## §1 三组是什么

| 组 | 由谁产生 | 内容 |
| --- | --- | --- |
| A 八行通知 | 产品 `renderOccurrence` | 头行 + 仓库 / 运行 / 工作流 / 分支 / 提交 / 结论 / 观察时间。**不含 job、step、文件、日志** |
| B 机械摘要 | 本实验 `digest.mjs`，零模型 | 三行固定模板：失败位置（失败 job / 失败 step）、改动文件（前 3 个 + 总数）、日志首个失败标记行。规则见 `samples.json` 的 `digestRules` |
| C 模型补充 | 产品当前 `attach()`，真材料 + 真端点 | 模型原文；被拒或失败时记录原因，不重试 |

B 组只用于实验，不接入产品。

**样本**（5 个，均未参与此前实验，`identity` 全部 `confirmed`）：

| run | 分支 | 失败形态 | 日志 | 改动文件 |
| --- | --- | --- | --- | --- |
| `38760836396` | main | `surface` job 单独失败（`test` 是绿的） | 65 536 字符 | 11 |
| `34752998965` | main | `test / Setup Node` 环境失败，无测试输出 | 2 996 字符 | 1 |
| `36327884462` | test/proactive-ci-outbound | 旧 workflow（8 步）在功能分支失败 | 65 153 字符 | 1 |
| `38765009721` | main | 常规测试失败，改动面很宽 | 65 536 字符 | 19 |
| `38415923320` | main | 常规测试失败，改动 1 个文件 | 65 536 字符 | 1 |

## §2 三组对比表

可用标识 = job / step / 文件标识，且能在材料里核实、且与材料真值一致（不指向不存在的 job、不把 step 挂到没失败的 job 下、不改动清单之外的文件）。

| run | A 可用标识 | B 可用标识 | C 附加 | C 失败类型 | C 模型耗时 |
| --- | --- | --- | --- | --- | --- |
| `34752998965` | 0 | 3 | 否 | refused-citation | 52 725 ms |
| `38760836396` | 0 | 5 | 否 | timeout（180 000 ms） | 180 005 ms |
| `36327884462` | 0 | 3 | **是** | attached | 132 018 ms |
| `38765009721` | 0 | 5 | 否 | timeout（180 000 ms） | 180 010 ms |
| `38415923320` | 0 | 3 | 否 | upstream-error | 168 379 ms |

合计：A **0/5** 有可用标识，B **5/5**，C **1/5** 附加。

A 组的 0 是结构性的：八行通知里根本没有 job / step / 文件字段，`renderOccurrence` 只渲染 run 级元数据。

## §3 逐 run 判读

### `34752998965`（Setup Node 环境失败，日志仅 2 996 字符）

- B：`失败位置：test / Setup Node` / `改动文件：docs/development/phase-1-runtime.md` / `日志首行：… ##[error]Dependencies lock file is not found …`
- C：未附加，`引用不可核验（1 处）`，52 725 ms。
- 判读：这是最短的一份材料，模型在 52 s 内就给出了回答，只是引用没有在材料里逐字找到。**这一条说明失败可以发生在引用校验，而不是模型说不出话。**产品在失败时不保留模型原文，所以本实验无法判断它当时想说什么——这是产品的一个可观测性缺陷，见 §7。

### `38760836396`（surface 单独失败）

- B：`失败位置：surface / Test the runtime` / 改动 11 个文件（列前 3）/ `日志首行：… ✖ 范围：声明里的根按 origin 的仓库名逐字命中才算 declared …`
- C：打满 180 000 ms，`超时`。
- 判读：这个样本最能体现「失败 job 不是 test」——B 直接说出 `surface`，A 完全看不出。C 没有产出。

### `36327884462`（唯一附加）

- B：`失败位置：test / Build and test` / `改动文件：test/proactive-ci-smoke.test.mjs` / `日志首行：… ✖ intentional proactive CI outbound smoke failure (1.215779ms)`
- C 原文：`建议补看作业步骤列表里的 Post Setup Node、日志摘要中的 skipped 92，以及日志末尾的 Node.js 20 is deprecated 警告；这些位置在通知建议之外。`
- C 的 cited：`Post Setup Node`、`skipped 92`、`Node.js 20 is deprecated`（3 条，其中 1 条落在结构性材料段，2 条只能从日志段取到）。
- 判读：**模型的三条建议都没有指向失败位置**。`Post Setup Node` 是 job 里存在但未失败的步骤；`skipped 92` 是日志里的跳过计数；`Node.js 20 is deprecated` 是运行环境的弃用警告。三者都是背景信息，不是失败原因也不是失败位置。而 B 的三行全部命中真值。
- 需要注意的一处规则产物：正则把 `Node.js` 当成了一个文件名标识（`\.js` 后缀），所以它在 `locusConsistency` 里计了一次「不一致」。这是标记规则的粗糙处，不是模型错误——但即使去掉它，模型仍然只有一条 job/step 级标识（`Post Setup Node`），且指向未失败的步骤。

### `38765009721`（宽改动）

- B：`失败位置：test / Build and test` / 改动 19 个文件（列前 3）/ `日志首行：… ✖ 端点：人问一句，常驻答一句，句子逐字回来 …`
- C：打满 180 000 ms，`超时`。
- 判读：这是材料最大的一条（19 个文件的 patch）。超时在直觉上与材料规模相关，但本实验没有测量 prompt 大小，不能把这条当因果。

### `38415923320`（窄改动）

- B：`失败位置：test / Build and test` / `改动文件：test/changeable-repositories.test.mjs` / `日志首行：… ✖ failing tests:`
- C：168 379 ms 后 `端点不可用`。
- 判读：产品的这句日志**不区分网络错误、非 2xx、响应读取失败**三种情况，所以本实验无法判断到底是什么。同一条 run 的日志只有 3 项材料、规模与 §3 第一条相近，因此不能归因为「材料太大」。

## §4 六项指标

| 指标 | 读数 |
| --- | --- |
| 首次附加率 | **1/5**（不重试） |
| 失败类型分布 | attached 1、timeout 2、upstream-error 1、refused-citation 1 |
| 模型耗时 | 附加 132 018 ms；未附加 52 725 / 168 379 / 180 005 / 180 010 ms |
| 定位一致性（仅附加样本） | 判 2 条，不一致 2 条（`Post Setup Node`、`Node.js`＝规则产物）；无一条指向真实失败位置 |
| 引用质量（仅附加样本） | 3 条 cited，1 条在结构性材料段、2 条只在日志段 |
| 模型相对机械摘要的增量 | **模型独有可用标识 0 条；机械摘要独有 3 条**（`job:test`、`step:Build and test`、`file:test/proactive-ci-smoke.test.mjs`） |

## §5 端点行为

同一端点在实验期间用 16 token 的短请求探测，1 262 ms 返回 200，说明服务在线。但五个样本的请求里有三次跑到 166–180 s 才失败。

此前同一模型的五样本实验（`experiments/ci-supplement-increment/`）是 5/5 附加、30–170 s 完成；本批是 1/5 附加。两次的差别是样本，不是端点配置。**本实验不能区分「这批材料让模型推理变长」与「端点在这段时间变慢」**，因为产品不记录 `prompt_tokens` / `completion_tokens` / `finish_reason`，而失败分支也不保留部分输出。

本批读数已登记为未解释项 `u-o7q6al`。

## §6 对「模型补充的实际增量价值」的判读

分三层说，避免把一件事说成三件：

1. **稳定性层**：在 180 000 ms 预算下，这批 5 个样本只有 1 次拿到可附加输出。若产品依赖这段补充，那么大多数时候人看到的仍然只有八行通知——而八行通知 0/5 含定位信息。
2. **内容层**：唯一产出的那一次没有提供定位，反而指向三处背景噪音。B 组在同一 run 上用三条确定性规则给出了正确的 job / step / 文件。
3. **证据层**：本批 n=5、成功 1，内容层的判断建立在 n=1 之上。它能支持「这段补充在此样本上没有增量」，**不能**支持「模型补充普遍没有增量」。

## §7 范围与限制

- **不是 §10.5 的 B 段独立验收**。B 段要求预注册协议与更大批次，并且调过提示词后必须换材料复测；本实验只回答「这一批上三组各自给出什么」。
- 单模型、单端点、一批冻结样本、每 run 一次调用。不覆盖其它模型、多轮、工具调用形态、温度变化。
- **模型失败时不保留原文**：引用不可核验与超时的样本拿不到模型说了什么，因此无法区分「模型答错」与「回答被校验误杀」。
- **失败原因不可诊断**：`端点不可用` 一句话覆盖三种底层原因，`超时` 不区分「模型仍在推理」与「连接卡住」。
- **标记规则有两处粗糙**：`Node.js` 被 `\.js` 后缀当成文件名；`log-span` 用 6-gram 滑窗求最长公共块，会把中英混排的通用词（如 `conclusion`）算成引用日志。这类命中不参与一致性判定，但会抬高「引用来自日志」的计数。
- 机械摘要是本实验的产物，**规则由我设计**，不是产品的既有能力。它对 `34752998965` 这种「日志里没有 `✖` 但有 `##[error]`」的样本依赖 MD-3 的正则；冻结时该正则锚定了行首，导致 0/5 命中，已按 `samples.json` 的 `amendments[MD-3]` 修正为不锚定行首（修正发生在任何成功的模型读数之前）。
- 本批耗时**不能**用来谈产品预算：模型调用都发生在 `attach()` 内，但材料读取只有 3–6 s，与 §13.12 那批一致；模型侧的行为与那批不同（见 §5）。

## §8 对 Q2 形态的建议

**仍然不建议现在就加第二道语义判据（建议–证据绑定）。** 理由不是「没有问题」，而是「本批的问题出在产不出与不定位，而不是出在建议与证据脱钩」：唯一附加的那一条，三条 cited 都在材料里逐字可查，它的问题是指向了背景噪音，而不是引用了不存在的东西。再叠一层语义判据挡不住这个。

**但本批指向一个更便宜的形态**：既然机械摘要用三条确定性规则就在 5/5 样本上给出正确的 job / step / 文件，而模型补充是 1/5 附加 + 0 定位增量，那么「先给确定性定位三行，再（可选）让模型解释」这个结构比「只有模型补充」更稳。这只是形态建议，**本轮不实现**（按裁决，零模型摘要仅用于实验），也不构成对提示词的调整。

如果要继续验证模型补充的价值，本批指向两件必须先解决的事：一是让失败分支留下模型原文与 `finish_reason`（否则永远无法判断是答错还是被杀）；二是把预算与材料规模的组合探明（本批 3 次打满，原因未知）。

## §9 复现

```bash
node experiments/ci-supplement-triangulate/groups.mjs      # A/B 两组，零模型，约 25 s
ONLY_RUN=<runId> node experiments/ci-supplement-triangulate/run-supplement.mjs  # C 组，单样本
node experiments/ci-supplement-triangulate/score.mjs       # 六项指标汇总
```

产物：`samples.json`（冻结的样本、规则、指标定义）、`groups.json`（A/B 文本与真值）、`results.json`（C 组原文与逐条指标）、`summary.json`（汇总）、`candidates.json`（候选筛选读数）。

`results.json` 里 `34752998965` 的记录来自脚本修好合并逻辑之前的一次运行（该次读数有效，按冻结规则不重跑），其 `materialsMs` 与 `groups.A/B` 为 `null`；A/B 两组文本由 `groups.json` 按同一份材料重算，材料内容不随时间变化。
