# dsh-file-mount 补测报告（净成本与认识风险）

> 承接 [report.md](report.md) 的五阶段兼容性测试。本文件回答三个问题：它是否正确、是否真的节省上下文、是否会损害 Hikari 对文件变化的认识。
> 全部数据来自 `session-12b5e144-62a0-4b92-9968-14acefbbddc9` 的真实事件（8 次 `read`、1 次 `edit`、1 次 `file_mount_forget`），字符数由 `fm-cost.mjs` 从 session 日志逐条统计。

## 0. 补测结论

| 问题 | 答案 |
|---|---|
| 它是否正确？ | **PASS（有 2 个设计特征）**：去重、变化检测、diff、强制重读均按设计工作；但「计数按文件、展示按范围」且「edit 后读回 diff 而非全文」 |
| 它是否真的节省上下文？ | **在本场景（10 行小文件）没有节省，基本持平（约 -2%）**；节省量由单次公式 `(F − C) − M` 决定，小文件为负 |
| 它是否会损害 Hikari 对文件变化的认识？ | **有真实风险**：多轮 diff 后模型没有合并后的完整快照；上下文压缩/截断时 diff 会失去锚点 |

### 1.2 无插件对照（同一批调用的理论值）

无插件时 8 次 `read` 每次返回全文（示例文件 10 行、约 390 字符/次，文件从 20 行增长到 22 行，取实测 382–398 的中位）：

- `A = 8 × 390 ≈ 3120 字符`

实测 `B ≈ 3054（仅 read）+ 74（forget）= 3128 字符`（`edit` 的 120 字符两边都有，不计入差异）。

**净差：B − A ≈ +8 字符，即没有节省，基本持平（本场景约 -2%～0%）。**

## 2. 它是否正确

### 2.1 行为正确性（PASS）

| 检查点 | 证据 | 结论 |
|---|---|---|
| 首次读取不被改写 | seq 34 是原生全文，插件只追加标记 | PASS |
| 同 hash 重复读短路 | seq 43、128 返回 `already mounted`，无正文 | PASS |
| 内容变化被检测 | hash `2a21c583→bc12d3a3→e6cc28e6→70863b34→b39fd116`，均触发 diff | PASS |
| diff 计数准确 | 2 行替换 = `+2/-2`；4 行替换 + 1 追加 = `+5/-4`（第 3 节详述） | PASS |
| 强制重读恢复全文 | seq 79 `Mount ledger entry forgotten` → seq 85 返回 21 行全文 | PASS |
| `edit` 后读不返回旧缓存 | seq 103 写入成功 → seq 109 返回新内容（diff L1） | PASS |

### 2.2 两个设计特征（不是 bug，但会影响使用）

1. **计数是文件级，展示是范围级**。
   - 第 3 轮：文件只改了 L3、L7（2 替换）+ 追加 L21，返回 `+3/-2`、只展示 L3/L7。
   - 第 8 轮：改 L2/L4/L6/L8（4 替换）+ 追加 L22，返回 `+5/-4`、只展示 L2/L4/L6/L8。
   - 规律：`+` 计入读取范围**外**的新增行（L21、L22），`-` 只计删除行；但展示只列读取范围（L1–L10）内的改动。模型看到 `+5` 却只看到 4 段，需要自己意识到「多出的 +1 在范围外」。
2. **`edit` 后读返回 diff，不是全文**。
   - seq 102 `edit` → seq 108 read → seq 109 只返回 `+1/-1` 的 L1 片段，没有 L2–L10。
   - 这符合「只补变化」的设计，但与「write 后读免单全文」的直觉不同；模型若要全貌仍须 `file_mount_forget` + read。

## 3. 它是否真的节省上下文

### 3.1 单次净节省公式

设：`F` = 无插件时返回全文的字符数；`C` = 插件返回内容的字符数；`M` = 挂载标记（user/message）的字符数。

```
单次净节省 = (F − C) − M
```

- 首次读：`C = F` → 节省 `−M`（倒亏）
- 同 hash 重复读：`C = P`（占位）→ 节省 `F − P − M`
- 变化读：`C = D`（diff）→ 节省 `F − D − M`

本场景实测：`F ≈ 390`，`P ≈ 213`，`D ≈ 180–276`，`M ≈ 120–142`。

- 重复读节省：`390 − 213 − 130 ≈ +47 字符`
- 变化读节省：`390 − 220 − 130 ≈ +40 字符`
- 首次读倒亏：`−130 字符`

8 次调用中 2 次全文（倒亏 260）、6 次省约 47（省 282）→ 净省约 22 字符，与 §1.2 的持平一致。

### 3.2 什么时候才省

只有当 `F` 远大于 `P + M` 时才划算：

- 读 100 行文件（F ≈ 4000）：重复读每次省 `4000 − 213 − 130 ≈ 3657 字符`，明显划算。
- 读 10 行小文件（F ≈ 390）：每次省 50 字符以内，且首次倒亏，整体接近零。

**结论**：dsh-file-mount 的收益与「单次读取返回的长度 F」成正比。Hikari 当前的读多为小范围、小文件（项目文档片段、单行 grep 结果），因此**不能假设它能降低 Hikari 的上下文成本**；它对大文件重复读有效，对小范围读无效甚至略亏。

## 4. 它是否会损害 Hikari 对文件变化的认识

### 4.1 真实风险：没有合并后的完整快照

第 8 轮之后，模型自己的观察（原话）：

> 累计来看，L1、L3、L5、L7、L9 以及本轮的 L2、L4、L6、L8 都已被逐次报告过，但我目前上下文里并不存在一份合并后的完整 L1–L10 快照；需要完整正文时仍应先 file_mount_forget 再 read。

这确认了：**多轮变化后，模型只有「首次全文 + 若干 incremental diff」**，要得到当前完整内容必须自己合并，或额外 `forget + read`（额外成本 `74 + 390 ≈ 464 字符`）。对 Hikari 来说这是有代价的：她判断「项目当前状态」时需要的正是完整内容，而不是增量。

### 4.2 更隐蔽的风险：diff 依赖上下文锚点

diff 的前提是「上次内容仍在上下文里」。如果：

- 会话被 compaction / 截断，更早的全文不在上下文；
- 模型把两次 diff 之间的未变化行张冠李戴；
- 工具结果被摘要化（如 Hikari 的 World/C-02 证据链）

那么 diff 就失去了锚点，模型看到的 `--- L3 ---` 片段无法与完整文件对应。这不是插件 bug，但它是「用增量替代全文」这一策略的固有风险。

### 4.3 不会损害的部分

- 内容变化本身不会被隐藏：hash 变化一定触发 diff，`+N/-M` 计数准确。
- 旧全文不会被改写：seq 34 的原始内容仍完整保留在 session 日志中（可作为证据回溯）。
- 强制重读可恢复全貌：`file_mount_forget` 行为正确。

## 5. 对 Hikari 的建议

1. **不作为 Hikari 的生产能力**（与你的判断一致：保留安装用于实验，不等于采纳）。
2. 若未来要采纳，只用于「大文件、重复读」场景，并且必须保留一条「需要全貌时 forget + read」的显式规则；不能把 diff 当作文件当前态。
3. 对 Hikari 当前的实际读模式（scoped-fs 下的项目文档片段），**不建议启用**：净成本接近零、首次读倒亏、且引入「无合并快照」的认识风险。
4. 无论是否采纳，这条实验数据支持一个更重要的结论：**文件读取的上下文优化必须按「读取返回长度」设计，而不是按「调用次数」设计**。
