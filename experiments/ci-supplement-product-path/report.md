# 产品路径上的 180 000 ms 预算：实测报告

**结论：够，但余量随端点波动在 16–55 s 之间摆动，最坏情形已经贴近边界。** 五个产品路径样本（两批）的补充耗时全部低于 180 000 ms：最短 124 639 ms、最长 163 638 ms。对应 `docs/architecture/ci-diagnosis-model-supplement-v0-boundary-review.md` §13.13 第 1 条——「180 000 ms 不是产品路径上的测量值」这条现在已经不成立了，但它换成了一个更弱的问题：余量够不够宽。

**本报告不宣布「验收通过」。** 测量执行成功；机器裁决通道不可用（见 §8），读数与时间戳提交 Human 审阅。

## 3. 时序全表与周期等式

### 3.1 关键边界（相对脚本起点，ms）

| 边界 | B#1 | B#2 | B#3 |
| --- | --- | --- | --- |
| cycle 开始（本轮第一次 acquisition） | 14 | 159 190 | 311 167 |
| 材料读取完成 | 5 192 | 165 093 | 316 497 |
| 补充完成（日志 `已附加`） | 158 176 | 310 162 | 474 805 |
| 投递（`deliver` 被调用） | 158 177 | 310 162 | 474 805 |
| cycle 结束 | 158 177 | 310 162 | 474 805 |
| 观察到的下一轮开始 | 159 190（= 158 177 + 1 013） | 311 167（= 310 162 + 1 005） | —（脚本在第三轮后主动停） |

### 3.2 周期等式（两批、四个独立观测点）

```
A: interval #1→#2 = 133 269 ms = 132 266（cycle#1） + 1 000（delayMs） + 3
B: interval #1→#2 = 159 176 ms = 158 163（cycle#1） + 1 000（delayMs） + 13
B: interval #2→#3 = 151 977 ms = 150 972（cycle#2） + 1 000（delayMs） + 5
```

四个观测点全部落在「上一轮 cycle 总时长 + delayMs + 3–13 ms」上，偏离均小于 0.01%。结构来源：

- `src/repository-ci-attention/plugin.ts:203-209` `scheduleCycle(delayMs)`：`pendingTimer = setTimeout(() => { pendingTimer = undefined; inFlight = runCycle(); }, delayMs)` —— **唯一**排下一轮的地方。
- `src/repository-ci-attention/plugin.ts:394-396` `finally { if (!stopped) scheduleCycle(config.delayMs); }` —— 下一轮在本轮 `runCycle()` **返回之后**才 arm。注释（`plugin.ts:200-203`）写明「a cycle is scheduled from the previous cycle's completion」，所以一轮慢，下一轮就晚，两者不可能重叠。
- 补充的位置：`plugin.ts:343` 记起点、`plugin.ts:345` `await supplement.attach(...)`、`plugin.ts:352` 记「已附加（X ms）」、`plugin.ts:360` `await delivery.deliver(lines)` —— 补充的 await 完整落在 cycle 内部，因此**整段等待直接推迟下一轮**。

**推迟量**：没有补充时一轮 cycle 是毫秒级（批次 B 两轮除材料与补充外的差额分别是 13 ms 与 1 ms）；有补充时是 151–164 s，**下一轮轮询推迟约 151–164 s**。由于 `github-ci` 只观察最新一条 run（`src/github-ci/github.ts:11` `?per_page=1`），这段窗口内出现的新红 run 不会被本轮看到；下一轮看到的只有那时的最新一条。

**对 180 000 ms 的结论**：

- **够。** 五个产品路径样本全部完成并附加，余量：47 737 / 55 361 / 21 840 / 29 029 / **16 362** ms（占预算 26.5% / 30.8% / 12.1% / 16.1% / **9.1%**）。受预算约束的模型段为 119 609–158 308 ms。
- **余量不稳定，且比历史样本看起来更紧**：同一批 run 在两天里相差 20–35 s。`38931770141` 在 §13.12 是 175 278 ms、A 批 124 639 ms、B 批 150 971 ms——同材料、同端点、同提示词，波动 50 s。**这是端点采样波动，不是产品路径的开销。**
- **什么条件下不够**：模型段越过 180 000 ms。历史最慢样本 175 278 ms 只剩 **4 727 ms**；本次 B 批最慢 163 638 ms 只剩 **16 362 ms**。也就是说，**按现有五个产品路径样本，最紧的一次余量不到 10%**。越过预算的行为是已定的：`supplement.ts:344` 记 `模型补充：超时（180000 ms）→ 未附加`，确定性消息照发（§10.5 A 段语义不变）。
- **预算没有覆盖的部分**：材料读取（5 030–5 902 ms）不在 `budgetMs` 内，但计入 cycle 总时长并推迟下一轮；所以「一轮最多 180 s」不成立，一轮的上界是 **材料耗时 + 180 s + 投递**。

## 6. 未覆盖

1. **五个样本、三个 run**，且都是 §13.12 的基线材料——按 §10.5 的限定，**不能**用来充当 B 段的独立验收。
2. **端点单实例、本机网络**：材料读取 5.0–5.9 s 是当前 GitHub 往返的良好值；更慢的网络会把 cycle 拉长（但不影响模型段是否超预算）。
3. **超时 / 取消 / 401 / 403 的真机分支仍未覆盖**。
4. **投递是假实现**，`deliver` 返回的耗时是毫秒级；真 pipe 客户端更慢时，cycle 会再加这部分。
5. 只跑了 `delayMs = 1000`；产品若用更大的 delay，轮询间隔按等式同比增加。
6. 端点波动 50 s，五个样本不足以界定最坏情形——**「余量 16 s」本身也是一个样本读数，不是下界**。

## 7. 对两条推翻条件的逐条核对

两条判断的推翻条件都在写计划时定死，这里逐条对照实际读数，不做事后放宽。

### 7.1「预算够用」——两个推翻条件都没触发

| 推翻条件 | 实际读数 | 结论 |
| --- | --- | --- |
| 日志出现 `模型补充：超时（180000 ms）→ 未附加` | 五轮日志（批次 A 2 轮、批次 B 3 轮）中该行出现 **0 次**；`cycle-log.json` 的 `timeouts` 计数为 0 | 未触发 |
| 模型段实测耗时 ≥ 180 000 ms | 五个模型段：126 882 / 119 609 / 152 984 / 145 069 / 158 308 ms；最大 158 308 ms，距 180 000 ms 余 21 692 ms | 未触发 |

限定必须一起读：**按补充总计看，最紧一次余量是 16 362 ms（B#3，9.1%）**；而历史样本里最慢一次是 175 278 ms（只剩 4 727 ms）。所以这条判断成立的范围是「这五个样本 + 同批材料规模、同端点、同提示词」，不是「任何情况下都够」。

### 7.2「周期串行自排」——两个推翻条件都没触发

| 推翻条件 | 实际读数 | 结论 |
| --- | --- | --- |
| `scheduleCycle` 不在 cycle 结束后的 `finally` 里 | `src/repository-ci-attention/plugin.ts:394-396` 就是 `finally { if (!stopped) scheduleCycle(config.delayMs); }`；唯一的 `setTimeout` 在 `plugin.ts:203-209`，`plugin.ts:200-203` 的注释写明「a cycle is scheduled from the previous cycle's completion」 | 未触发 |
| 相邻两轮开始之差与「cycle 时长 + delayMs」偏离 > 10% | 三个观测点：133 269 = 132 266+1 000+3（偏差 0.002%）、159 176 = 158 163+1 000+13（0.008%）、151 977 = 150 972+1 000+5（0.003%）；另两次直接测量下一轮起点落在上一轮 cycle-end + 1 013 / 1 005 ms | 未触发 |

两个推翻条件合起来排除了「还有别的东西占着时间」这一替代解释：三个样本、两批运行、两种观测方式（相减与直接打点）都指向同一个等式，且源码里排下一轮的位置是唯一的。
