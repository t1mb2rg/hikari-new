# M2-d 报告：记忆检索的匹配粒度

> 问题：M2-c 真实验证里，会话 B 用自己的措辞去查会话 A 写下的记忆，**四次全空**。这是「检索工具不在」的问题，还是「匹配口径太窄」的问题？
>
> 结论：**字面口径部分够。** 把匹配从「整串子串」放宽成「拉丁词元包含 + 中文片段覆盖率 ≥ 0.25」，B1 那四条现场 query 在只有一条记录时**全部命中**，同时七条无关 query 一条都没被误命中；但纯换义词、纯英文问法、单字 query 三类字面天花板仍然打不穿——那是 M2-e 的题目，不是阈值能解决的。
>
> 状态：冻结面 `docs/architecture/m2d-memory-matching-interface-freeze.md` 已实施并验证（`hikari-native/memory/recall.js`），验证记录在 `docs/development/m2d-verification.md`。改动**尚未提交**。

## 1. 现场是什么样

M2-c 的会话 B 拿到的是会话 A 写下的 954 字记忆（正文含「修订只能改链头，旧记录永不改」，另有源码行号与三个局限）。它依次问了：

| 次序 | query（原文） | 走哪个工具 | 当时结果 |
| --- | --- | --- | --- |
| 1 | `hikari 记忆修订` | `search_memories` | 空 |
| 2 | `revise memory 旧记录` | `search_memories` | 空 |
| 3 | `记忆修订 只能修订哪一条 旧记录是否改动` | `search_memory`（findings 侧） | 空 |
| 4 | `记忆 修订 约定` | `search_memories` | 空 |

会话 B 后来改用 `get_memory` 直接读（它手里有 id），闭环才走通。而会话 B 上一次（会话 B0）能命中，用的措辞是 `Memory 修订约定` 和 `修订`——**两个字不差时命中，换个说法就 0**。这正是整串子串的特征。

## 2. 比了几种字面口径

探针 `experiments/m2d-matching/probe.mjs` 只读真实存储（`experiments/m2c-live/store/memory.jsonl`），在同一批 query 上跑 12 种口径。query 共 19 条：B1 四条原文、B2 两条历史命中措辞、B1 变体 2、同义改写 3、跨语言 2、无关 6（其中 12 条是「期望命中」）。

| 口径 | 两行快照：命中 | 两行：误命中 | 一行快照（B1 当时）：命中 | 一行：误命中 |
| --- | --- | --- | --- | --- |
| A 整串子串（现状） | 2/12 | 0 | 2/12 | 0 |
| B 切词多词与（全部词都要出现） | 4/12 | 0 | 4/12 | 0 |
| F0.25 片段覆盖率（单片段退回子串） | 10/12 | **3** | 10/12 | 3 |
| E0.25 拉丁词元 + 中文片段 0.25 | **10/12** | **0** | **10/12** | **0** |
| E0.30 | 9/12 | 0 | 9/12 | 0 |
| E0.34 | 7/12 | 0 | 7/12 | 0 |
| D0.34 单字覆盖率 | 12/12 | **4** | 12/12 | 4 |
| D0.50 单字覆盖率 | 12/12 | **4** | 12/12 | 4 |

逐格矩阵在 `experiments/m2d-matching/matching-probe.md`（19 行 × 12 列）。三条读数决定了取舍：

1. **纯片段（F）会假阳性。** `TypeScript 编译错误` 在正文里以 `pe`/`es`/`ri`/`pt` 命中（4/12 = 0.33），`npm test 跑多久` 靠 `np`/`pm`/`te`/`es`/`st` 命中（5/7 = 0.71）——后者来自 `appendinput`、`development/m2`、`writeFile`/`update`/`delete`、`supersedes`、`store`。拉丁字母的 bigram 在代码词里遍地都是。
2. **单字覆盖率（D）性质上不可用。** `完全不存在的词` 靠「完/不/存/在/的」拿到 0.71，而片段层面只中「存在」1/6。
3. **加上「拉丁词元必须被正文词元包含」以后，误命中归零**（E0.25 的 0 误命中），而命中数不降——因为被挡掉的都是拉丁撞车，不是真实命中。

## 3. 阈值为什么是 0.25

E 档三个阈值只差几条 query，差异落在哪里是可核对的：

| query | 中文片段 | 覆盖率 | 0.25 | 0.30 | 0.34 |
| --- | --- | --- | --- | --- | --- |
| `memory 修订 规则 是什么` | `修订`/`规则`/`是什`/`什么` | 1/4 = 0.25 | 中 | 不中 | 不中 |
| `hikari 记忆修订` | `记忆`/`忆修`/`修订` | 1/3 = 0.33 | 中 | 中 | 不中 |
| `记忆修订` | `记忆`/`忆修`/`修订` | 1/3 = 0.33 | 中 | 中 | 不中 |

0.25 是能同时保住这三条的**唯一**一档，且不引入误命中。它的代价是「只要命中一个片段就可能进结果」——所以强度要参与排序：整串命中（1）永远排在片段命中（≤0.99）之前，同强度再按 `seq` 新到旧。

## 4. 字面救不回来的三类

| 类型 | 例子 | 实测 | 性质 |
| --- | --- | --- | --- |
| 纯换义 | `两次修改同一条记忆` | 与正文只共用「同一」一个片段（1/8 = 0.125，低于 0.25）；A/B/F/E 全 0；只有单字覆盖率 D0.34/D0.50 能靠单字过线（那是假阳性，不是召回） | 不是阈值问题 |
| 跨语言 | `how to revise a memory without losing history` | 拉丁词元 `how`/`without`/`history` 不在正文词元里 | 正文全中文时必然 0 |
| 单字 query | `记忆` | 正文没有「记忆」这个串（写的是「修订约定」） | 退回子串即 0 |

这三类要解决就得换机制，三条出路各自的代价（详见 `docs/architecture/m2d-memory-matching-interface-freeze.md` §7）：

| 出路 | 代价 |
| --- | --- |
| 中文分词 + 同义词表 | 5–20 MB 词典随插件分发、同义表人工维护；分词边界错就召回抖动，表扩太宽等于用误命中换召回；覆盖率单位从 bigram 变词，0.25 必须重新标定 |
| 多语嵌入 | 本地 100–400 MB 模型或每次远端调用；`store.mjs` 要加向量列与索引；模型版本漂移导致同一 query 结果变化；记忆正文离开进程（隐私面变大）；余弦阈值与字面强度不可直接比较，需融合规则 |
| LLM 语义重排 | 每次检索一次模型调用（延迟秒级、有费用）、结果不可复现、同步工具要等模型；而且只能重排候选，救不回首轮 0 召回 |

三条都会改动强度定义或验收，等于重开冻结面——所以留给 M2-e，不在本片里加"可选开关"。

## 5. 落地了什么

- **冻结面**：`docs/architecture/m2d-memory-matching-interface-freeze.md`（状态「已评审并实施」，§4 已按实测回填行号）。§3 的四处修订**已经写进** `docs/architecture/m2c-memory-discovery-interface-freeze.md` 正文：§2.1 的匹配口径（`:79`）与排序（`:83`）、§6 第 1 条（`:177`）与第 3 条（`:179`），并在该文件文首加了 M2-d 修订说明（`:8`）。文档里不再有「契约说子串、实现按片段」的分叉。
- **实现**：`hikari-native/memory/recall.js` 新增 `matchStrength(query, text)`（整串 → 1；拉丁词元须全中；中文 bigram 覆盖率 ≥ 0.25，上限 0.99；只有拉丁词元且整串不是子串 → 0.5），`matchMemories` 改为强度优先排序；工具描述改成如实口径（说清「整串最高、片段次之、不做分词/同义/语义、跨语言不匹配」）。
- **验证**：`node --test hikari-native/test/memory-recall.test.mjs` 16 pass（原 12 条原样通过 + 新增 4 条：强度表、B1 四条现场 query 全中、七条无关 query 全空、强度与同强度排序）；全量 `npm test` 1135 tests / 1131 pass / 0 fail / 4 skip；`node experiments/m2d-matching/crosscheck.mjs` 用**实施后的**函数重放探针 19 条 query，与 E0.25 列逐格一致（10/12、0 误命中、不一致 0）。

改动只碰 `recall.js` 与其测试文件：工具名、五键结果、分页、错误码、`store.mjs`、其余五个工具都没动。

## 6. 这个结论在哪里成立

- 成立范围：`profile = hikari-verify`、`model = deepseek-account/deepseek-flash`、存储里 1–2 条中文记忆、query 由真人会话与构造两类构成。语料只有两条记录，阈值 0.25 的稳健性没有在更大语料上验过。
- 不成立的地方：正文以英文为主时，中文片段规则不适用（本片没测）；记录量级变大后 O(n) 全表扫的代价没测；跨进程并发修订的分叉风险与检索无关，仍按 M2-b 的结论处理（无文件锁）。
- 可复现：`node experiments/m2d-matching/probe.mjs`、`node experiments/m2d-matching/probe.mjs --records=1`、`node experiments/m2d-matching/crosscheck.mjs`。

## 7. 待人决定

1. **提交这批改动**（`recall.js` + 测试 + 冻结面 + 验证文档 + 报告 + 探针）。未提交前，仓库行为仍是整串子串。
2. **阈值 0.25 是否接受**：它在 19 条 query 上 0 误命中，但样本只有 1–2 条记录。若不接受，可只冻结排序维度（强度 = 整串/片段两档）而不冻结数值——代价是 `memory 修订 规则 是什么` 会落空。
3. **是否把 `score` 纳入返回值**：现在强度只用于排序。若要让模型自己判断「这条有多接近」，得加键，那是返回形状变更，本片明确不做。
